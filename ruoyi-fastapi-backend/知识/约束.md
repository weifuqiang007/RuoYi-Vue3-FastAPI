## 约束：实体类字段必须标注语义注释

所有与数据库映射的实体类（DO）和与前端交互的实体类（VO）中，**每个字段必须标注清晰的语义注释**，说明字段含义、取值范围和业务用途。

### DO 层（SQLAlchemy ORM 模型）

1. **类级 docstring**：用一句话说明该表的业务用途
2. **`__table_args__`**：设置 `comment` 参数作为数据库表注释
3. **每个 `Column()` 必须有 `comment='...'`**：说明字段含义
4. **枚举/状态字段**：必须在 comment 中注明所有可选值，格式为 `comment='状态（0正常 1停用）'`
5. **JSON/数组字段**：应在 comment 中说明数据格式并给出示例值

### VO 层（Pydantic 模型）

1. **每个字段必须使用 `Field(..., description='...')`**：description 内容应与 DO 层 `comment` 保持一致
2. **枚举字段优先使用 `Literal` 类型**：如 `Literal['0', '1']`，在 description 中注明含义
3. **`model_config` 必须设置 `alias_generator=to_camel`**：确保 Python 下划线命名自动转换为前端驼峰命名
4. **必须设置 `from_attributes=True`**：支持从 SQLAlchemy ORM 对象直接创建 Pydantic 实例

### ❌ 反面示例（禁止）

```python
# DO 层 —— 缺少 comment
class RagChunk(Base):
    """RAG文档分块表"""
    __tablename__ = 'rag_chunk'
    chunk_id = Column(BigInteger, primary_key=True)  # ❌ 无 comment
    del_flag = Column(CHAR(1), server_default='0')    # ❌ 不知道 '0' 代表什么
```

```python
# VO 层 —— 缺少 description、Literal、to_camel
class DocumentResponseModel(BaseModel):
    """文档响应"""
    doc_id: int                      # ❌ 无 Field(description=...)
    parse_status: str = '0'          # ❌ 无 description、无 Literal 类型
```

### ✅ 正确做法

**DO 层：**

```python
class EduTask(Base):
    """教学任务表 —— 教师创建反身性研究任务，配置各区知识库和AI参数，发布到指定班级"""
    __tablename__ = 'edu_task'
    __table_args__ = {'comment': '教学任务表'}

    task_id = Column(BigInteger, primary_key=True, autoincrement=True, comment='任务主键ID')
    task_name = Column(String(200), nullable=False, comment='任务名称，如"张大爷案例行动研究"')
    status = Column(CHAR(1), default='0', comment='任务状态（0草稿 1已发布 2已截止 3已归档）')
    scenario_kb_ids = Column(JSONB, comment='情境区使用的知识库ID列表，JSON数组如[1,2]')
```

**VO 层：**

```python
class RecordVO(BaseModel):
    """学习记录详情响应"""
    record_id: int = Field(..., description='学习记录主键ID')
    current_stage: Optional[str] = Field(None, description='当前阶段（scenario/decision/reflection/research/submitted/completed）')
    scenario_status: Optional[str] = Field(None, description='情境区完成状态（0未开始 1进行中 2已完成）')

    model_config = ConfigDict(alias_generator=to_camel, from_attributes=True)
```


## 约束：数据库 DDL 必须包含字段注释

所有数据库建表 SQL（包括新建表和修改表结构的 DDL）中，**每个字段和表本身都必须包含 `comment` 注释**。

### 核心规则

1. **表级注释**：`CREATE TABLE` 语句末尾必须有 `comment = '表业务含义'`
2. **字段级注释**：每个字段定义后必须有 `comment '字段含义'`
3. **枚举值注释**：状态类、类型类字段必须注明所有可选值，格式为 `comment '字段名（0值A 1值B）'`
4. **注释一致性**：DDL 中的 `comment` 必须与 DO 层 `Column(comment=...)` 保持一致，避免两层描述不同步

### ✅ 正确做法

```sql
create table edu_task (
  task_id      bigint       not null auto_increment    comment '任务主键ID',
  task_name    varchar(200) not null                   comment '任务名称，如"张大爷案例行动研究"',
  status       char(1)      default '0'                comment '任务状态（0草稿 1已发布 2已截止 3已归档）',
  create_time  datetime     default current_timestamp  comment '创建时间',
  ...
) engine=innodb comment = '教学任务表';
```


## 约束：查询接口必须明确业务查询条件

开发查询类接口时，必须根据业务场景明确所有合理的查询条件，而非照搬数据库字段。

### 设计流程

1. **理解业务场景**：先确认"谁在什么场景下需要查什么数据"，再推导查询参数
2. **AI 辅助初稿**：前期可由 AI 根据接口语义和业务上下文初步定义查询参数，后续根据实际需求调整
3. **查询参数必须封装为 VO**：查询参数 ≥3 个时，必须创建 Pydantic QueryModel（详见下方"Controller 层参数约束"）
4. **每个查询字段必须写 `description`**：注明是精确匹配、模糊匹配还是范围查询

### 查询字段类型规范

| 查询类型 | 说明 | 示例 |
|---|---|---|
| 精确匹配 | 传入值与数据库值完全一致 | `status: Literal['0','1'] = Field(None, description='任务状态（精确匹配）')` |
| 模糊匹配 | 传入值作为关键字模糊搜索 | `task_name: str = Field(None, description='任务名称（模糊匹配）')` |
| 范围查询 | 传入起止值界定范围 | `begin_time: str = Field(None, description='创建开始时间（YYYY-MM-DD）')` |


## 约束：接口变更必须检查并生成变更文档

每次修改接口代码后，**必须主动检查入参和出参是否发生变化**。如果发生变化，必须在指定目录下创建或更新变更文档，不得延后或遗漏。

### 检查流程

1. **修改完成后立即自检**：对比修改前后的入参/出参结构，确认是否有新增、删除或类型变更
2. **如有变更，立即生成文档**：在 `fanshenxingwendang/接口变更文档/` 目录下创建或更新变更文档
3. **即使本次修改不涉及入参/出参，也应在提交前确认**：避免遗漏隐式变更（如修改了 VO 字段类型但未更新文档）

### 文档模板要求

每份接口变更文档必须包含以下内容：

1. **版本号 + 日期**：格式 `VX.Y`，日期格式 `YYYY-MM-DD`
2. **接口信息**：URL、HTTP方法、接口名称
3. **变更类型**：新增接口 / 入参变更 / 出参变更 / 接口废弃
4. **变更内容**：
   - 新增/修改/删除了哪些参数
   - 参数的含义、类型、是否必填
5. **前端需要做的事情**：明确告诉前端工程师需要改什么
6. **测试用例**：给出 curl 或请求示例，方便前端验证


## 约束：Controller 层参数必须使用 Pydantic VO 模型，禁止手写参数列表 + if-else 组装

当接口有多个查询参数（≥3个）时，**必须**在 `entity/vo/` 下创建对应的 Pydantic 查询模型，
并通过 FastAPI 的 `Annotated[QueryModel, Query()]` 自动解析，**禁止**在 Controller 中手写一长串 `Optional` 参数再逐个 `if` 组装。

### ❌ 反面示例（禁止）

```python
@task_controller.get('/student/list')
async def get_student_tasks(
    creator_type: Optional[str] = None,
    task_name: Optional[str] = None,
    dept_id: Optional[int] = None,
    teacher_name: Optional[str] = None,
    # ... 继续写一堆 ...
    page_num: int = 1,
    page_size: int = 10,
) -> Response:
    filters = {}
    if creator_type:
        filters['creator_type'] = creator_type
    if task_name:
        filters['task_name'] = task_name
    # ... 继续一堆 if ...
```

### ✅ 正确做法

**第一步**：在 `entity/vo/xxx_vo.py` 中定义查询模型

```python
class TaskListQueryModel(BaseModel):
    """任务列表查询条件"""
    creator_type: Optional[str] = Field(None, description="任务类型：'0'教学任务 / '1'自研课题")
    task_name: Optional[str] = Field(None, description='任务名称（模糊匹配）')
    dept_id: Optional[int] = Field(None, description='归属班级ID')
    # ... 其他查询字段 ...
```

**第二步**：在 Controller 中用 `Query()` 自动解析

```python
from fastapi import Query

@task_controller.get('/student/list')
async def get_student_tasks(
    request: Request,
    query_db: Annotated[AsyncSession, DBSessionDependency()],
    current_user: Annotated[CurrentUserModel, CurrentUserDependency()],
    query: Annotated[TaskListQueryModel, Query()],
    page_num: int = 1,
    page_size: int = 10,
) -> Response:
    # model_dump(exclude_none=True) 自动过滤掉未传的参数
    filters = query.model_dump(exclude_none=True)
    result = await TaskService.get_student_tasks(
        query_db, current_user.user.user_id, class_id,
        roles=current_user.roles, filters=filters or None,
        page_num=page_num, page_size=page_size,
    )
    return ResponseUtil.success(data=result)
```

### 核心要点

1. **查询参数≥3个时必须用 VO**：少量参数（1-2个）可以直接写在函数签名中，超过3个必须创建 QueryModel
2. **VO 字段必须写 description**：用 `Field(None, description='...')` 标注每个字段含义
3. **Controller 中一行搞定**：`Annotated[QueryModel, Query()]` 让 FastAPI 自动解析 URL query params
4. **用 `exclude_none=True` 过滤**：`query.model_dump(exclude_none=True)` 只保留用户实际传入的字段


## 约束：全局统一使用项目日志模块

项目中所有业务代码**必须**使用统一的日志模块，禁止自行创建 Logger 实例。

### 导入方式

```python
from utils.log_util import logger
```

### 核心规则

1. **禁止使用标准库 `logging` 创建 Logger**：不允许 `logging.getLogger(__name__)`、`logging.info()` 等直接调用
2. **禁止在文件级别创建独立 Logger 实例**：所有模块必须通过统一的 `from utils.log_util import logger` 获取
3. **日志级别由环境统一控制**：开发环境 `DEBUG`，生产环境 `INFO`，通过 `.env.*` 配置文件切换，代码中不得硬编码日志级别

### 背景原因

- 项目使用 Loguru 作为日志引擎，通过 `InterceptHandler` 将标准库 `logging` 的输出统一接管
- 日志级别、输出格式（文本/JSON）、文件轮转策略（50MB 切片、30 天保留、zip 压缩）、敏感数据脱敏等能力均在 `utils/log_util.py` 中集中管理
- 如果模块自行创建 Logger，将绕过上述所有统一配置，导致开发/生产环境日志行为不一致、脱敏失效、日志格式混乱

### 唯一例外

当需要**配置第三方库的日志级别**时（如抑制 SQLAlchemy 的 DEBUG 输出），允许使用 `logging.getLogger('third.party.name').setLevel(...)`，这不属于业务日志范畴。

### ❌ 反面示例（禁止）

```python
import logging
logger = logging.getLogger(__name__)  # ❌ 绕过了统一的日志配置
```

```python
import logging
logging.info("操作完成")  # ❌ 直接调用 logging 模块方法
```

### ✅ 正确做法

```python
from utils.log_util import logger

logger.info("操作完成")
logger.error("处理失败: {}", error_msg)
logger.debug("调试信息: key={}", key)
```
