## 问题1：sql 的基础问题

```python
from sqlalchemy import select, update, delete
from sqlalchemy.ext.asyncio import AsyncAttrs, AsyncSession
from module_rag.entity.do.knowledge_base_do import RagKnowledgeBase

class KnowledgeBaseDao:

    @classmethod
    async def get_by_id(cls, db: AsyncSession, kb_id: int) -> RagKnowledgeBase | None:
        result = await db.execute(select(RagKnowledgeBase).where(RagKnowledgeBase.kb_id == kb_id,
                                                                 RagKnowledgeBase.del_flag == '0'))
        return result.scalars().first()

    @classmethod
    async def get_list(cls, db: AsyncSession) -> list[RagKnowledgeBase]:
        result = await db.execute(
            select(RagKnowledgeBase).where(RagKnowledgeBase.del_flag == '0').order_by(RagKnowledgeBase.create_time.desc())
        )
        """
        把 Result 转换成 可迭代的 ORM 对象序列。
        相当于：只取查询结果里的 “实体行”，不要元组。
        """
        return list(result.scalars().all())


    @classmethod
    async def create(cls, db:AsyncSession, kb: RagKnowledgeBase) -> RagKnowledgeBase:
        db.add(kb)
        await db.flush()
        return kb
```
await db.flush()不用给kb赋值吗？不应该是kb = db.flush()这种的吗？不然kb怎么能收到db.add的结果的回调?

### 回答
不需要。这是 SQLAlchemy 的工作机制，和普通函数返回值不同：

db.add(kb) 做了什么：把 kb 对象挂到 SQLAlchemy 的会话（Session）里，此时 kb 处于 "pending" 状态，还没有 kb_id。

await db.flush() 做了什么：把会话里所有待处理的对象同步到数据库（执行 INSERT），数据库生成自增主键后，SQLAlchemy 自动回填到原对象上。也就是说 kb 这个 Python 对象的 kb.kb_id 已经有值了。


kb = RagKnowledgeBase(kb_name="test", ...)  # kb.kb_id = None
db.add(kb)          # kb 挂进 session，但还没 INSERT
await db.flush()    # 执行 INSERT，数据库返回 kb_id=1，SQLAlchemy 自动回填给 kb
print(kb.kb_id)     # 1 ← 已经有值了
return kb           # 直接返回就行
flush() 返回的是 None，不是数据库行。它是一个副作用操作——修改的是传入的 kb 对象本身的状态。这是 SQLAlchemy ORM 的核心设计：对象是"活的"，被 session 跟踪，flush 后自动同步。


## 问题2：`_startup_hooks` 这个 list 在哪赋值的？只看到定义没看到赋值。还有，新加 module 要不要写 hooks.py？

```python
# common/lifecycle.py
_startup_hooks: list[tuple[str, Callable[['object'], Awaitable[None]]]] = []   # 第24行：定义为空

class LifecycleHooks:
    @classmethod
    def register_startup(cls, name: str):
        def decorator(fn):
            _startup_hooks.append((name, fn))   # 第39行：唯一的写入点
            return fn
        return decorator
```
全仓 grep `_startup_hooks =` 只看到第 24 行那处初始化，看不到"赋值"。那它什么时候被填满的？另外以后新加一个 module，是不是也得写一个 hooks.py？

### 回答

先记住**两个让这一切成立的 Python 机制**（这是"看不懂时序"的根因），理顺这两个，时序就自然通了。

#### 机制一：装饰器在"import 时"就执行，不是"调用函数时"执行

`@xxx` 是语法糖。看 `module_learning/hooks.py:21`：
```python
@LoginPolicyHooks.register_login_validator('edu_registration_audit')
async def check_registration_audit(query_db, user_id): ...
```
等价于：
```python
async def check_registration_audit(query_db, user_id): ...
# 下面这行赋值，发生在 Python 执行到这一行的瞬间：
check_registration_audit = LoginPolicyHooks.register_login_validator('edu_registration_audit')(check_registration_audit)
```
关键点：**底下那行赋值，是在这个 .py 文件被 import 的那一刻发生的**——不是等有人调用 `check_registration_audit()` 时才发生。而 `register_login_validator(...)` 函数体内部干的事就是 `_login_validators.append(...)`。

> 结论：**"import hooks.py"这个动作本身，就把名字塞进 list 了。** 不需要任何人去"调用"那个函数。

#### 机制二：list 是"可变的、按引用共享的"，append 是原地改

`_login_validators` 在 `common/login_policy.py:33` 定义为空 list。这个 list 对象一旦创建，任何拿到它引用的代码都能往里塞东西，而且 `.append()` 是**原地修改**，不产生新 list、不重新赋值。

所以你 grep `_login_validators =`（或 `_startup_hooks =`）只能看到定义处那一行，看不到任何"赋值"——因为**根本没人重新赋值**。它是被 `.append()` 一次次塞满的，这是个**副作用**，不是赋值。

> 一句话总结：**"定义一次为空" + "import 时的副作用 append" = list 被填满。** 中间没有第三步赋值，所以 grep 不到。

#### 比喻：钉在墙上的报名表

- `_login_validators` / `_startup_hooks` = 一张钉在墙上的**报名表**，一开始空白（定义空 list）。
- `@register_login_validator` / `@register_startup` = 框架发给所有人的**笔**（装饰器）。
- 框架**不会**挨个敲门问"你要不要报名"。它在启动时**沿着走廊把每个 `hooks.py` 的门打开一遍**（`discover_and_load` 扫描 `module_*/hooks.py` 并 import 它们）。门一开（import 触发），里面的 `@register...` 那行自动执行 = 报名人自己拿笔在表上签名（append）。
- 真正运行起来后（启动 / 登录时），框架**读这张表**，按签名顺序逐个执行（`run_startup` / `run_login_validators`）。

#### 完整时序（以登录校验为例——这是当前真正接了线的活例子）

```
后端启动
└─ server.create_app()                                              # server.py
     └─ LifecycleHooks.discover_and_load()                          # server.py:175
          └─ 扫描 module_*/hooks.py，逐个 importlib.import_module     # common/lifecycle.py:58
               │
               ├─ import module_learning/hooks.py
               │    └─ 执行 @LoginPolicyHooks.register_login_validator('edu_registration_audit')   # module_learning/hooks.py:21
               │         └─ _login_validators.append(('edu_registration_audit', check_registration_audit))  # common/login_policy.py:48
               │
               └─ （module_rag/hooks.py 已不存在，跳过）

之后每次有用户登录：
└─ LoginService.authenticate_user(...)
     └─ LoginPolicyHooks.run_login_validators(db, user_id)          # 遍历 _login_validators 逐个 await
          └─ check_registration_audit(db, user_id) 被调用 → 查注册审核状态
```

启动钩子 `_startup_hooks`（`common/lifecycle.py`）是**完全相同**的模式：定义在 `:24`、append 在 `:39`、被同一个 `discover_and_load`（`:58`）触发。只是**目前没有业务模块注册启动钩子**（MinIO 已提升为框架基础设施 `config/get_minio.py`，预热直接由 `server.py` lifespan 调用，不走这个机制），所以它是"待命"状态、list 为空。

### 新加一个 module，要不要写 hooks.py？

**不强制。** 取决于这个模块有没有"需要框架在启动时 / 登录时替我执行一段代码"的逻辑：

| 场景 | 要不要 hooks.py |
|---|---|
| 只加 HTTP 接口（controller / service / dao） | **不用写**。`auto_register_routers` 会自动发现 `module_xxx/controller/*.py`，接口自动上线。 |
| 启动时要初始化某资源（预热向量库、加载模型、建外部连接） | **要写**。在 `module_xxx/hooks.py` 里用 `@LifecycleHooks.register_startup('名字')` 注册一个 async 函数。 |
| 登录时要加一道校验（如会员到期、token 额度） | **要写**。在 `module_xxx/hooks.py` 里用 `@LoginPolicyHooks.register_login_validator('名字')` 注册。 |
| 两者都没有 | **不用写**。`discover_and_load` 扫不到 `module_xxx/hooks.py` 就自动跳过，啥也不影响。 |

关键认知：**hooks.py 是"可选的自注册入口"，不是模块的必需品。** 框架永远不直接 import 具体的 `module_xxx`，它只扫"有没有叫 `hooks.py` 的文件"——有就打开（import → 触发装饰器报名），没有就略过。这正是"框架定机制、业务自注册、互不耦合"的实现方式。

#### 模板：给新模块加一个启动钩子（复制即用）

新建 `module_xxx/hooks.py`：
```python
from common.lifecycle import LifecycleHooks

@LifecycleHooks.register_startup('xxx_warmup')
async def warmup(app) -> None:
    """启动时初始化 xxx。失败会被 run_startup 吞成 warning，不阻断整体启动。"""
    # 你的初始化逻辑写这里……
```
就这一步。`discover_and_load` 会自动发现它，`server.py` **无需任何改动**。登录校验同理，把 `register_startup` 换成 `LoginPolicyHooks.register_login_validator` 即可（注意后者是 **fail-fast**——抛 `LoginException` 会阻断登录，不能被吞）。
