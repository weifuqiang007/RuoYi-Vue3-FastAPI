# 部署问题

> 本文档记录「研修班知识管理系统」（RuoYi-Vue3-FastAPI）**首次打包上线**的过程、踩过的问题与解决，并把这些经验**提炼为约束**，供：
> 1. 本项目未来继续打包时参考、自检；
> 2. 未来其他项目在打包上线与代码管理上**提前做约束**，避免重复踩坑。
>
> 操作层面的具体命令见 `fanshenxingwendang/部署运维/线上部署手册_打包上传与版本更新流程.md`；本文聚焦「为什么、注意什么、约束什么」。

## 一、本次打包上线复盘（2026 年 6 月）

### 1.1 架构与部署形态

| 层 | 技术 | 部署形态 |
|---|---|---|
| 前端 | Vue3 + Vite | 本地 `npm run build:prod` 出 `dist/`，由**宿主机 nginx**（编译安装）托管 |
| 后端 | FastAPI | 源码上传，服务器 `docker build` 成镜像，`docker run` 跑容器 |
| 数据库/缓存/对象存储 | PostgreSQL / Redis / MinIO | 服务器**已有的 docker 容器**，不动 |

访问链路：`浏览器 → nginx(:15348) → 前端静态 / 反代 /prod-api → 后端容器(:9099→宿主:15349) → postgres/redis/minio`。

### 1.2 过程回顾

1. 本地准备部署文件：`Dockerfile.prod`、`.dockerignore`、调整 `.env.prod`；
2. 前端 `npm run build:prod` 打包 `dist`；后端源码 `tar` 打包；
3. 上传服务器，解压到 `/mnt/zhangyichi/{backend,web/dist}`；
4. 后端 `docker build` + `docker run`；
5. nginx 加 server block + reload；
6. 防火墙放行 `15348`；
7. 验证 → 踩坑 → 逐个修复 → 跑通。

### 1.3 踩过的问题（现象 → 根因 → 解决 → 约束化）

#### 问题 1：容器启动报 `ruoyi: command not found`

- **现象**：后端容器一启动就退出，`ruoyi` 命令不存在。
- **根因**：`ruoyi` 命令由 `pyproject.toml` 的 `[project.scripts] ruoyi = "cli.main:main"` 注册，**必须 `pip install .`（安装项目本体）** 才会生成。项目自带的 `Dockerfile.pg` 只 `pip install -r requirements`，漏装项目本体。
- **解决**：`Dockerfile.prod` 增加 `RUN pip install --no-cache-dir .`。
- **→ 约束**：见 [约束：Dockerfile 必须安装项目本体以注册 CLI 入口](#约束dockerfile-必须安装项目本体以注册-cli-入口)。

#### 问题 2：后端连不上数据库 / Redis / MinIO

- **现象**：后端日志报 PostgreSQL/Redis 连接超时或拒绝。
- **根因**：`.env.prod` 里 host 写的是**公网 IP `115.220.6.150`**。后端跑在 docker 容器里，从容器访问「宿主机公网 IP」再绕回宿主机上的 postgres 容器，会被防火墙卡住，且等于把数据库端口暴露公网，既不通又不安全。
- **解决**：host 改为 `host.docker.internal`（容器内特指宿主机），`docker run` 加 `--add-host=host.docker.internal:host-gateway`。前提 Docker ≥ 20.10。
- **→ 约束**：见 [约束：容器访问宿主机服务必须用 host.docker.internal，禁止公网 IP 回环](#约束容器访问宿主机服务必须用-hostdockerinternal禁止公网-ip-回环)。

#### 问题 3（核心）：接口 404 —— `/prod-api/captchaImage` Not Found

- **现象**：前端页面能打开，点登录所有接口 404。后端日志一度出现 `/prod-api/prod-api/captchaImage`（两层前缀）。
- **诊断关键**：`curl http://127.0.0.1:15349/prod-api/captchaImage`（绕过 nginx 直连后端）**也是 404**；而 `curl http://127.0.0.1:15349/captchaImage`（裸路径）返回 200。证明问题不在 nginx、不在前端，在**后端路由形式**。
- **根因**：后端是**裸路由**（路由挂在 `/captchaImage`），`APP_ROOT_PATH=/prod-api` 只是 Swagger 文档的**元数据**，**不会自动给路由加前缀**（dev 环境 vite proxy 也是 rewrite 剥掉 `/dev-api` 再转后端，印证了这点）。所以 nginx 必须把 `/prod-api` 前缀**剥掉**再转给后端，后端才认。
- **解决**：nginx `proxy_pass` **末尾带 `/`**：
  ```nginx
  location /prod-api/ {
      proxy_pass http://localhost:15349/;   /* 末尾的 / 会用 / 替换掉 /prod-api/，剥掉前缀 */
  }
  ```
  - 末尾**空**（`http://localhost:15349`）→ 原样转发，保留 `/prod-api` → 后端 404；
  - 末尾**带 /**（`http://localhost:15349/`）→ 剥掉 `/prod-api` → 后端命中。
- **→ 约束**：见 [约束：反代前缀必须与后端路由策略对齐](#约束反代前缀必须与后端路由策略对齐)。

#### 问题 4：AI 流式生成卡住、不逐字输出

- **根因**：nginx 默认 `proxy_buffering on`，会把 SSE/流式响应攒着一起返回。
- **解决**：后端反代 location 加 `proxy_buffering off;` + `proxy_http_version 1.1;` + `proxy_set_header Connection "";`。

#### 问题 5：刷新前端子路由页面 404

- **根因**：Vue Router 是 history 模式，刷新子路由时 nginx 找不到对应文件。
- **解决**：前端 location 加 `try_files $uri $uri/ /index.html;`。

#### 问题 6：文件/资料上传报 413

- **根因**：nginx 默认 `client_max_body_size 1m`，文档上传超限。
- **解决**：前端、后端两个 location 都加 `client_max_body_size 1024M;`。

#### 问题 7：打包产物 / 截图差点混入 git 仓库

- **现象**：`git add -A` 时 `backend.tar.gz`、`web-dist.tar.gz`、`page*.png` 截图、`chrome-a11y-cdp/` 调试产物都是未跟踪文件，差点一起提交。
- **解决**：`.gitignore` 补 `*.tar.gz`、`page*.png`、`chrome-a11y-cdp/`、`Aspose.Words.*.png`。
- **→ 约束**：见 [约束：打包产物与调试产物必须纳入 .gitignore，禁止入库](#约束打包产物与调试产物必须纳入-gitignore禁止入库)。

## 二、打包上线注意事项（自检清单）

### 2.1 打包前自检

- [ ] `.env.prod`（线上环境配置）的 DB/Redis/MinIO host 是否为 `host.docker.internal`（**不是公网 IP**）；
- [ ] `Dockerfile.prod` 是否含 `pip install .`（注册 CLI 命令）；
- [ ] `.dockerignore` 是否排除了 `__pycache__/build/logs/文档/tests`；
- [ ] 前端 `.env.production` 的 `VITE_APP_BASE_API` 是否与后端 `APP_ROOT_PATH`、nginx location 三者**前缀一致**；
- [ ] `.gitignore` 是否排除了 `*.tar.gz`、截图、调试产物。

### 2.2 nginx 配置自检

- [ ] `proxy_pass` 末尾是否带 `/`（剥前缀）—— **最易错**；
- [ ] `proxy_buffering off`（流式接口）；
- [ ] `try_files $uri $uri/ /index.html`（history 路由）；
- [ ] `client_max_body_size` 够大（文件上传）；
- [ ] 端口不与服务器现有应用冲突。

### 2.3 启动后验证

```bash
# 后端直连（裸路径），返回 JSON 即后端正常
curl -i http://127.0.0.1:<后端端口>/captchaImage
# 经 nginx（带前缀），返回 JSON 即反代 + 前缀剥离正常
curl -i http://127.0.0.1:<nginx端口>/prod-api/captchaImage
```
再浏览器实测登录、文件上传、AI 流式生成三个关键路径。

## 三、Git 管理规范（本项目）

### 3.1 分支策略：稳定部署分支 + 开发分支

| 分支 | 角色 | 规则 |
|---|---|---|
| `打包上线` | **稳定部署基线**，永远是「能上线」的状态 | **只进不出**：只通过 `cherry-pick` 接收成熟改动，**禁止在上面直接开发** |
| `决策区代码`（等开发分支） | 日常开发 | 自由提交，小步快跑 |

### 3.2 日常发版工作流（cherry-pick「一点一点合」）

```bash
# ① 开发：切到开发分支，小步提交
git checkout 决策区代码
...改代码...  git commit -m "xxx功能"

# ② 上线：挑成熟提交合进打包上线
git checkout 打包上线
git cherry-pick <commit哈希>          # 一个一个挑，对应「一点一点合」
git push                              # 同步到远程备份

# ③ 从 打包上线 分支打包部署（按部署手册）
```

> **为什么用 cherry-pick 而不是 merge**：merge 会把开发分支**全部**历史合进来，无法「只上某些改动」；cherry-pick 能精确挑选要上线的提交。前提是**开发时多做小步 commit**，才好挑。

### 3.3 提交规范

- **小步提交**：一个功能/一个修复一个 commit，便于 cherry-pick 挑选；
- **message 说人话**：`新增/修复/优化 + 模块 + 简述`，如「修复 RAG 文档上传分块丢失问题」；
- **不混提交**：业务代码、部署配置、文档尽量分开提交，方便回滚和挑选。

### 3.4 敏感信息

- `.env.prod` 含数据库密码、JWT 密钥等，**已纳入版本控制**（项目既有做法）。若仓库可能公开，应改为 `.env.prod.example`（占位）+ 本地真实文件 `.gitignore` 排除；
- 不要把真实密码/密钥写进 commit message、文档示例、聊天记录。

## 四、通用前置约束（适用于未来其他项目）

> 以下约束由本次实战提炼，**与具体项目无关**，新项目打包上线/代码管理时应提前遵守。

### 约束：Dockerfile 必须安装项目本体以注册 CLI 入口

若应用通过 `pyproject.toml` 的 `[project.scripts]` 注册了 CLI 命令（如 `ruoyi`、自定义启动命令），Dockerfile 中**必须** `pip install .` 安装项目本体，仅 `pip install -r requirements.txt` 不会生成该命令。

✅ 正确：
```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
RUN pip install .          # ← 注册 CLI 命令
CMD ["mycli", "run"]
```

### 约束：容器访问宿主机服务必须用 host.docker.internal，禁止公网 IP 回环

容器内访问「与本容器同在一台宿主机上的其他服务」时，host 必须用 `host.docker.internal`，并在 `docker run` 加 `--add-host=host.docker.internal:host-gateway`（Docker ≥ 20.10）。

❌ 禁止：host 写宿主机公网 IP（防火墙易卡、数据库暴露公网不安全）。
⚙️ 兜底：Docker 版本过低不支持 host-gateway 时，改用默认网关 `172.17.0.1`。

### 约束：反代前缀必须与后端路由策略对齐

部署前**必须先确认后端路由是「裸路由」还是「带前缀路由」**，据此决定 nginx 反代是否剥前缀——这是接口 404 最高发的根因。

- **后端裸路由**（路由 `/captchaImage`，前缀仅文档元数据）→ nginx 必须**剥前缀**：`proxy_pass http://backend/;`（末尾带 `/`）；
- **后端带前缀路由**（路由 `/api/captchaImage`）→ nginx **原样转发**：`proxy_pass http://backend;`（末尾空）。

诊断方法：`curl` 裸路径和带前缀路径分别打后端，看哪个返回 200。

### 约束：流式 / 大文件 / 长连接接口必须在反代层特别处理

涉及 SSE 流式输出、大文件上传、长耗时接口时，nginx 反代 location 必须配置：
- `proxy_buffering off;`（流式必须关，否则攒着不输出）；
- `proxy_http_version 1.1;` + `proxy_set_header Connection "";`；
- `proxy_read_timeout` / `proxy_send_timeout` 放宽（如 600s）；
- `client_max_body_size` 按最大上传体设置。

### 约束：history 路由前端必须配 try_files 兜底

前端若用 history 路由模式（非 hash），nginx 静态 location 必须有 `try_files $uri $uri/ /index.html;`，否则刷新子路由 404。

### 约束：上线前必须有独立的稳定部署分支

任何要打包上线交付的项目，**必须**维护一个独立的「部署/发布」分支：
- 该分支只接收经过验证的改动（cherry-pick 或合并），**永远保持可部署**；
- 日常开发在开发分支进行，禁止直接在部署分支上开发；
- 每次从该分支打包部署，保证「上线的就是分支上的」。

### 约束：打包产物与调试产物必须纳入 .gitignore，禁止入库

`.gitignore` 必须排除：
- 打包产物：`*.tar.gz`、`*.zip`、`dist/`、`build/`；
- 调试/截图产物：截图、录屏、`chrome-a11y-cdp/` 等调试目录；
- 环境产物：`__pycache__/`、`*.egg-info/`、`.venv/`、`node_modules/`、`logs/`。

提交前用 `git status` 复核，确认无产物文件混入。

### 约束：环境配置与代码分离

线上配置（`.env.prod` 等）与代码分离管理：
- 环境差异项（host、端口、密钥、开关）全部走 `.env.*`，**禁止硬编码进代码**；
- 切换环境只改 `.env` 文件 / 启动参数，不改代码；
- 敏感信息（密码、密钥）不写入文档示例、commit message。

### 约束：每次打包上线必须留可复现的部署文档

每个项目必须有一份**可复现**的部署文档（命令可直接复制执行），至少包含：环境信息、架构、首次部署步骤、日常更新流程、常见错误排查、完整配置文件附录。文档随项目演进同步更新。

## 五、新项目部署 Checklist（通用）

立项/首次部署时按此清单逐项确认：

- [ ] 确认部署形态（前端静态托管方式、后端容器/裸跑、依赖服务来源）；
- [ ] 准备 `Dockerfile`（含 `pip install .` / 对应的项目安装步骤）+ `.dockerignore`；
- [ ] 环境配置文件 `.env.prod`，host 用 `host.docker.internal`；
- [ ] 前端 build 前缀 = 后端 root_path = nginx location 前缀，三者对齐；
- [ ] 确认后端路由形式（裸/带前缀），据此定 nginx 是否剥前缀；
- [ ] nginx 配置：剥前缀、`proxy_buffering off`、`try_files`、`client_max_body_size`；
- [ ] 端口规划，避开服务器已占用端口；
- [ ] `.gitignore` 排除产物/截图/环境垃圾；
- [ ] 建立独立「部署分支」，开发分支分离；
- [ ] 编写可复现的部署文档；
- [ ] 启动后三项验证：直连后端、经反代、浏览器实测（登录/上传/流式）。
