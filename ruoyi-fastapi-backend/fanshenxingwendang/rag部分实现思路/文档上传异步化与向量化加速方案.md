# 文档上传异步化与向量化加速 —— 完整方案

> 范围：知识库管理 → 文档管理 → 上传文档 → 确定（`POST /rag/document/upload/{kb_id}`）
> 痛点：大文件上传后，后端解析 + 分块 + 向量化耗时极久，HTTP 请求长时间挂起直至超时。
> 目标：上传秒回、处理后台化、进度可见、向量化提速。
> 关联代码：
> - 前端 [src/api/rag/document.js](../../../ruoyi-fastapi-frontend/src/api/rag/document.js) `uploadDocument`
> - 前端 [src/views/rag/document/index.vue](../../../ruoyi-fastapi-frontend/src/views/rag/document/index.vue) `submitUpload`
> - 后端 `module_rag/controller/document_controller.py` `upload_document`
> - 后端 `module_rag/service/document_service.py` `upload_document` / `process_document`
> - 后端 `module_rag/service/embedding_service.py` `embed_texts`
> - 后端 `module_rag/entity/do/document_do.py` `RagDocument`
> - 后端 `config/get_scheduler.py` `SchedulerUtil`

---

## 一、问题诊断

### 1.1 当前调用链（全同步阻塞）

```
前端 确定 ─► POST /rag/document/upload/{kb_id} (multipart, 整文件)
                         │
        DocumentController.upload_document
                         │
        DocumentService.upload_document
                         │
   ┌─────────────────────┴──────────────────────┐
   │ ① await file.read()        # 整文件读进内存 │
   │ ② minio.put(...)           # 上传 MinIO     │
   │ ③ DB 建记录 + doc_count+1                   │
   │ ④ await process_document()  ← ★ 罪魁祸首    │
   │     ├ MinIO 下载回临时文件（刚传又下）        │
   │     ├ parser.parse()        # 解析          │
   │     ├ FixedChunker.chunk()  # 分块          │
   │     ├ ChunkDao.bulk_insert  # 存分块        │
   │     ├ EmbeddingService.embed_texts  ← 最慢  │
   │     └ ChunkDao.bulk_update_embeddings      │
   └─────────────────────────────────────────────┘
                         │
                    HTTP 200 返回（此时才算完成）
```

**致命点**：第 ④ 步 `await cls.process_document(...)` 在同一个请求上下文里**同步**跑完整条流水线。向量化 `embed_texts` 对智谱 API 串行打批次（`BATCH_SIZE=25`，每批带 3 次重试 + sleep），一份几百块的文档就要几十秒到几分钟，HTTP / nginx / 浏览器任何一层超时都会断。

### 1.2 三大耗时点

| 阶段 | 耗时来源 | 量级 |
|---|---|---|
| 上传 | 整文件 `read()` 进内存 + 单次 multipart 上传 | 大文件秒级~十秒级，受带宽限制 |
| 解析 | `parser.parse`（PDF/DOCX），CPU 密集 | 几秒~几十秒（PDF 尤其慢） |
| 向量化 | `embed_texts` 串行调智谱 API，每批 25 条带 sleep | **分钟级**，绝对主因 |

### 1.3 一句话根因

> "文件接收"和"重型处理"被绑在同一个同步请求里；重型处理（向量化）又是外部 API 串行调用，没有任何异步化与进度反馈机制。

---

## 二、设计目标

1. **上传秒回**：上传接口只负责"收文件 + 落库 + 触发处理"，几百毫秒内返回 `doc_id`。
2. **处理后台化**：解析/分块/向量化移出请求上下文，由后台 worker 执行。
3. **进度可见**：前端能轮询到 `parse_status` / `embed_status` / 进度百分比。
4. **向量化提速**：批次并发化，单批失败不影响整体。
5. **可靠可重试**：worker 崩溃 / API 失败后状态明确，用户可一键重试。

---

## 三、可复用的现有资产（不要重造轮子）

| 资产 | 位置 | 复用方式 |
|---|---|---|
| 状态机字段 | `rag_document.parse_status` / `embed_status`（0待处理→1中→2完成→9失败） | 直接作为任务状态，前端轮询依据 |
| 错误记录字段 | `rag_document.error_msg` | 后台任务失败落库 |
| 调度框架 | `config/get_scheduler.py` `SchedulerUtil`（APScheduler + Redis + Leader 选举 + ProcessPoolExecutor） | 承载后台任务、保证多 worker 单一执行 |
| 批量向量化 | `EmbeddingService.embed_texts`（已分批 + 重试） | 在此基础上加并发 |
| 对象存储 | `MinioUtil` | 文件中转（处理时下载到临时文件） |

## 四、总体架构（异步化后）

```
前端 确定 ─► POST /rag/document/upload/{kb_id}  ──► 200 {doc_id, parse_status:'0'} （毫秒级）
                                                         │
                                          (后台触发，不阻塞响应)
                                                         ▼
                              ┌─────────── 后台 Worker (APScheduler) ───────────┐
                              │  process_document(doc_id)                        │
                              │   parse_status: 0→1→2   实时写 progress          │
                              │   embed_status:  0→1→2   实时写 progress          │
                              │   失败 → 9 + error_msg                            │
                              └──────────────────────────────────────────────────┘
                                                         ▲
前端轮询  GET /rag/document/status/{doc_id} ─────────────┘  (每 2~3s)
        ◄── {parse_status, embed_status, progress, chunk_count, error_msg}
```

上传与处理彻底解耦：上传是"快事务"，处理是"慢后台任务"，两者通过 `rag_document` 表的状态字段通信。

## 五、分阶段实施

### 阶段 0：上传链路本身（文件传输优化）

> 目的：即便异步化，大文件上传本身也要稳，否则文件还没传完就谈不上处理。

**0.1 流式读取，避免整文件进内存**

现状 `content = await file.read()` 把整份大文件读进内存。改为流式写 MinIO（若 MinioUtil 支持 `put_stream`，否则分块读取拼接）：

```python
# document_service.upload_document 内
# 旧：content = await file.read(); minio.put(object_name, content)
# 新：边读边写，统计大小
file_size = 0
with tempfile.NamedTemporaryFile(delete=False, suffix=file_type) as tmp:
    while chunk := await file.read(8 * 1024 * 1024):  # 8MB 一块
        tmp.write(chunk)
        file_size += len(chunk)
    temp_path = tmp.name
minio.put_file(object_name, temp_path)   # 新增按路径上传方法
```

**0.2 前端上传进度条 + 无超时**

```js
// src/api/rag/document.js
export function uploadDocument(kbId, file, onProgress) {
  const formData = new FormData()
  formData.append('file', file)
  return request({
    url: `/rag/document/upload/${kbId}`,
    method: 'post',
    data: formData,
    headers: { 'Content-Type': 'multipart/form-data' },
    timeout: 0,                 // 上传不设超时
    onUploadProgress: onProgress // (e) => percent = Math.round(e.loaded*100/e.total)
  })
}
```

`submitUpload` 里把 `:loading="uploading"` 替换为真实进度条（`el-progress`），上传完成（拿到 doc_id）即关闭弹窗、列表出现该文档"处理中"行。

**0.3 网关/服务端体积限制**
- nginx：`client_max_body_size 2048m;`（按最大文件调）
- FastAPI：`UploadFile` 默认无硬限，确认反代链路每一层都放宽。

**0.4（可选）分片上传 + 断点续传**
- 仅在文件经常 > 200MB 或网络不稳时再做。方案：前端 `spark-md5` 算 hash → 切片 → 并发上传 → 合并接口。属于独立增强，不阻塞主线。

### 阶段 1：处理异步化（核心，立即解决超时）

> 这是性价比最高的一步：改动小，直接消灭"请求超时"。

**1.1 上传接口立即返回，不再 await 处理**

```python
# document_service.upload_document —— 把最后一步从「同步处理」改成「投递后台」
# 旧：
#   await cls.process_document(db, doc.doc_id)
#   return doc
# 新：
await DocumentDao.update_status(db, doc.doc_id, parse_status="0", embed_status="0")
await db.commit()   # 确保状态先落库，前端立刻能查到「待处理」
cls._dispatch_process(doc.doc_id)   # 投递后台，不 await
return doc
```

**1.2 后台任务投递机制 —— 三选一**

| 方案 | 机制 | 可靠性 | 改动 | 适用 |
|---|---|---|---|---|
| **A. `asyncio.create_task`** | 当前 worker 进程内起协程 | 低（worker 重启则任务丢，但状态留在「1」可重试） | 最小 | **起步首选**，先解决超时 |
| **B. APScheduler 一次性任务** | `scheduler.add_job(..., trigger=DateTrigger())`，复用 Leader + 持久化 jobstore | 高（崩溃恢复、多 worker 单一执行） | 中 | 生产推荐 |
| C. Celery / 独立队列 | 新组件 | 高 | 大 | 不推荐（与现有 APScheduler 重复） |

**推荐路径：A 起步 → 验证后升 B。** 两者对外接口完全一致，只是 `_dispatch_process` 内部实现不同。

方案 A（起步）：

```python
# document_service.py
import asyncio

@classmethod
def _dispatch_process(cls, doc_id: int):
    """投递文档处理到后台。方案A：当前进程协程。"""
    asyncio.create_task(cls._run_process_safe(doc_id))

@classmethod
async def _run_process_safe(cls, doc_id: int):
    """独立 session（脱离请求生命周期），统一兜底。"""
    try:
        async with async_session_factory() as db:
            await cls.process_document(db, doc_id)
    except Exception as e:
        logger.error(f"后台处理文档 {doc_id} 异常: {e}")
        async with async_session_factory() as db:
            await DocumentDao.update_status(db, doc_id, parse_status="9", embed_status="9", error_msg=str(e)[:500])
```

> ⚠️ 关键：`process_document` 现在用的 `db` 来自请求的 `AsyncSession`，请求返回后 session 即关闭。异步化后**必须用独立新建的 session**（`async_session_factory()`），否则会报 session closed。

方案 B（生产，复用现有 scheduler）：

```python
@classmethod
def _dispatch_process(cls, doc_id: int):
    """方案B：通过 APScheduler 投递一次性任务，Leader 执行、崩溃可恢复。"""
    from config.get_scheduler import scheduler, SchedulerUtil
    from apscheduler.triggers.date import DateTrigger
    if not SchedulerUtil._is_leader:
        # 非 Leader worker：直接起本进程协程兜底（参考 execute_scheduler_job_once 既有做法）
        asyncio.create_task(cls._run_process_safe(doc_id))
        return
    scheduler.add_job(
        func=cls._run_process_safe,
        trigger=DateTrigger(),
        args=[doc_id],
        id=f"rag_doc_process_{doc_id}",
        replace_existing=True,
        jobstore='sqlalchemy',   # 持久化，重启可恢复
        executor='default',
    )
```

**1.3 新增状态查询接口**

**1.4 进度字段（可选但强烈建议）**

`parse_status`/`embed_status` 只是粗粒度阶段。要显示"向量化 67%"，给 `rag_document` 加一列：

```sql

`RagDocument` 加 `progress = Column(Integer, nullable=True, server_default='0', comment='处理进度')`。

`process_document` 在分块、每批向量化的循环里更新：

# Step 2 分块后
total = len(all_chunks)
await DocumentDao.update_status(db, doc_id, embed_status="1", progress=10)

# Step 4 向量化，每完成一批推进进度
for i, batch_start in enumerate(range(0, len(texts), BATCH_SIZE)):
    ...本批 embedding...
    pct = 10 + int(90 * (batch_start + len(batch)) / total)

```

### 阶段 2：向量化提速（治本，缩短实际处理时间）

> 异步化解决"等"，本阶段解决"慢"。

**2.1 批次并发**（最有效）

现状 `embed_texts` 串行打批次。改为 `asyncio.gather` 受控并发（注意智谱 API 限流，并发数建议 3~5）：

```python
# embedding_service.embed_texts
CONCURRENCY = 4

@classmethod
async def _embed_batch(cls, client, batch):
    for retry in range(3):
        try:
            resp = await client.embeddings.create(model='embedding-3', input=batch, dimensions=1024)
            return [item.embedding for item in resp.data]
        except Exception as e:
            if retry == 2: raise
            await asyncio.sleep(1 * (retry + 1))

@classmethod
async def embed_texts(cls, texts):
    client = cls._get_client()
    batches = [texts[i:i+cls.BATCH_SIZE] for i in range(0, len(texts), cls.BATCH_SIZE)]
    sem = asyncio.Semaphore(cls.CONCURRENCY)
    async def guarded(b):
        async with sem:
            return await cls._embed_batch(client, b)
    results = await asyncio.gather(*(guarded(b) for b in batches))
    # 按批次顺序还原
    return [vec for batch_vec in results for vec in batch_vec]
```

数百块的文档，理论上从"分钟级"压到原来的 1/CONCURRENCY。

**2.2 单批失败不连坐**

`asyncio.gather` 默认一批抛错全部失败。改为 `return_exceptions=True`，对失败批次标记并继续，最后只把成功向量入库，失败块记到 `error_msg` 或单独的 `rag_chunk.embed_status`，支持局部重试。

**2.3 消除"传完又下载"的浪费（可选）**

`process_document` Step 0 把刚传上 MinIO 的文件又下回来。阶段 0 若已流式落临时文件，可在投递后台任务时**把临时文件路径作为参数传入**，省一次 MinIO 往返（需注意 worker 重启场景下临时文件可能不在，此时回退到从 MinIO 下载）。属于锦上添花，不阻塞主线。

### 阶段 3：可靠性与体验（进阶）

| 项 | 做法 |
|---|---|
| 重试按钮 | 列表 `embed_status='9'` 行显示"重试"，调 `POST /rag/document/reprocess/{doc_id}` 重新 `_dispatch_process`（`process_document` 已幂等：开头 `ChunkDao.delete_by_doc_id` 清旧块） |
| 列表自动刷新 | 列表存在 `parse_status in ('0','1') or embed_status in ('0','1')` 的行时，前端每 3s 轮询列表（或仅轮询未完成行的 status），全部完成停止 |
| Worker 崩溃恢复 | 升级到方案 B（持久化 jobstore）；或在启动时扫一次 `parse_status='1' or embed_status='1'` 的"卡死"记录，重新投递（加 `update_time` 超时判定，避免误重投正在跑的） |
| 进度推送（可选） | 用 SSE/WebSocket 替代轮询，实时推 progress。当前规模下轮询已够，非必须 |

## 六、接口契约变更

| 接口 | 变更 | 说明 |
|---|---|---|
| `POST /rag/document/upload/{kb_id}` | **语义变更** | 不再等处理完成。响应 `{doc_id, parse_status:'0', embed_status:'0'}` 立即返回 |

## 九、风险与回滚

| 风险 | 应对 |
|---|---|
| 异步化后 session 误用（报 closed） | `_run_process_safe` 必须新建独立 session |
| 后台任务在非 Leader worker 投递丢失 | 方案 A 下用 `create_task` 在当前 worker 跑（不依赖 Leader）；方案 B 下持久化兜底 |
| 向量化并发触发 API 限流 | `CONCURRENCY` 从 3 起步观察；保留单批重试 |
| 状态卡在"1"（worker 中途崩） | 启动扫描 + 超时重投（阶段3） |
| 回滚 | 上传接口恢复 `await process_document` 即回到旧行为；状态字段不影响 |

## 附：最小可行改动（如果只做一件事）

只想立刻止血，**只做阶段 1.1 + 1.2 方案A**：
1. `upload_document` 末尾 `await cls.process_document` → `cls._dispatch_process(doc_id)`（不 await）

三处改动即可让"大文件上传不再超时"，后续优化可逐步叠加。
