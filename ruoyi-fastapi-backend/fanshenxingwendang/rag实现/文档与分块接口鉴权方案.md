# 文档与分块接口鉴权方案（复用知识库作用域）

> 分支：`feature/kb-permission-scope`
> 状态：**设计阶段（仅文档，不改代码）**
> 关联接口：`module_rag/controller/document_controller.py`、`module_rag/controller/chunk_controller.py`
> 配套文档：`知识库权限控制设计方案.md`（知识库本体已按其落地，见 `common/aspect/resource_scope.py` + `module_rag/service/kb_scope_policy.py`）
> 日期：2026-07-08

---

## 0. 背景与现状

知识库本体的四级可见性（public/school/class/personal）已通过框架层 `common/aspect/resource_scope.py`（机制）+ 业务层 `module_rag/service/kb_scope_policy.py`（规则）落地。检索接口 `/rag/retrieval/search` 也已用 `KnowledgeBaseService.filter_accessible_ids` 做了 `kb_ids` 越权防护。

但**文档**和**分块**两个控制器目前只有路由级角色校验：

```python
# document_controller.py / chunk_controller.py
dependencies=[
    PreAuthDependency(),
    RoleInterfaceAuthDependency(['admin', 'teacher']),   # 只要是 admin/teacher 就能进
]
```

所有端点**没有任何可见性判断**，存在成片越权。

### 0.1 资源层级关系

```
RagKnowledgeBase (kb_scope / scope_dept_id / owner_user_id)   ← 已鉴权
  │   RagDocument.kb_id          （外键指向知识库）
  ├── 文档 RagDocument                                            ← 未鉴权
  │     │   RagChunk.doc_id / RagChunk.kb_id
  │     └── 分块 RagChunk                                          ← 未鉴权
```

关键事实：**文档与分块自身没有 scope 字段**，它们的可见性 100% 由所属知识库决定。

> 推论（本方案的核心）：**用户能访问某文档/分块 ⇔ 用户能访问其所属的知识库**。因此判定逻辑可直接复用 `KbScopePolicy.can_access(principal, kb)`，无需为文档/分块新建任何 ScopePolicy。

## 1. 越权点清单（逐接口）

### 1.1 `/rag/document/*`

| # | 接口 | 现状（service 调用） | 越权后果 |
| --- | --- | --- | --- |
| D1 | `GET /rag/document/list` | `get_doc_list(db, kb_id=None)` → `DocumentDao.get_all` 返回全部 | 任意 teacher 看到全平台所有文档元数据 |
| D2 | `GET /rag/document/list/{kb_id}` | `get_doc_list(db, kb_id)` 直查不校验 | 看任意 kb 的文档列表 |
| D3 | `POST /rag/document/upload/{kb_id}` | `upload_document(db, kb_id, file, user_id)` 不校验 | 往他人/他校 kb 投递文档 |
| D4 | `GET /rag/document/download/{doc_id}` | `get_file(db, doc_id)` 按 id 直查 | **越权下载他人文档文件** |
| D5 | `GET /rag/document/preview/{doc_id}` | `get_presigned_url(db, doc_id)` 按 id 直查 | **越权获取 MinIO 预签名 URL** |
| D6 | `DELETE /rag/document/{doc_ids}` | `delete_documents(db, ids)` 不校验 | 删除他人知识库的文档 |

### 1.2 `/rag/chunk/*`

| # | 接口 | 现状 | 越权后果 |
| --- | --- | --- | --- |
| C1 | `GET /rag/chunk/list/{doc_id}` | `get_page_by_doc(db, doc_id, ...)` 不校验 | **越权读取他人知识库的分块内容（检索片段原文）** |
| C2 | `PUT /rag/chunk` | `update_chunk(db, data)` 不校验 | **越权篡改他人分块内容并触发重新向量化** |

> D4/D5/C1 是数据泄露高危（文件本体 / 预签名 URL / 切片原文直接外泄）；C2 是数据完整性破坏。

## 2. 设计原则：从属资源复用父资源策略

### 2.1 为什么不新建 Policy

框架层 `ScopePolicy` 的三个抽象方法是 `build_principal / visible_filter / can_access`，描述的都是「**主体 × 资源**」的可见性规则。文档/分块的规则与知识库**完全同构**（没有独立的 scope 维度），若另建 `DocScopePolicy`，其 `can_access` 内部仍是「先查 doc.kb_id → 再判 kb」，纯属重复。

因此：

- **principal 注入复用**：文档/分块接口直接用 `principal: KbPrincipal = ViewerDependency('rag.knowledge_base')`。身份判定（school_id / class_id / taught_class_ids / owned_student_ids）和知识库完全一样，是同一套教育领域主体。
- **判定复用**：拿到 `principal` 后，调用 `_policy().can_access(principal, kb)` 即可。

### 2.2 需要补的能力：从属资源的间接鉴权

知识库接口是「**直接**拿 kb 判 `can_access(principal, kb)`」；文档/分块接口是「**间接**」——多一步「把 doc_id/chunk_id 解析成 kb」。这步当前框架没有现成封装，但在业务层写一个工具函数即可，**不必动框架**（见 §5 的 Rule of Three 判断）。

两类操作：

| 操作类型 | 判定方式 | 适用接口 |
| --- | --- | --- |
| **单条访问**（详情/下载/预览/改/删前置） | 取资源 → 解析 kb_id → 取 kb → `can_access(principal, kb)` 不通过则 403 | D2/D3/D4/D5/D6、C1/C2 |
| **列表过滤** | 用 kb 的 `visible_filter` 作子查询，过滤 doc/chunk 的 `kb_id` | D1/D2（列表） |

## 3. 权限矩阵（沿用知识库四级，应用于从属资源）

文档/分块的可见性 = 其所属 kb 的可见性，矩阵与《知识库权限控制设计方案 §1.2》一致：

| 查看者 ＼ 所属 kb | public | school | class | personal |
| --- | :-: | :-: | :-: | :-: |
| admin | ✅ | ✅ | ✅ | ✅（全部） |
| 教师（同校） | ✅ | ✅ | ✅（同校） | ✅ 仅归属学生本人 |
| 教师（他校） | ✅ | ❌ | ❌ | ❌ |
| 学生 | ✅ | ✅（本校） | ✅（本班） | ✅ 仅本人 |

## 4. 待确认的设计决策（已给推荐值）

- **Q1 学生能否管理文档/分块**：当前路由是 `['admin','teacher']`，学生被挡在外面。但学生有个人级知识库，理应能管理自己 kb 的文档。
  - **推荐**：列表/上传/下载放开 `student`，由 service 层 `can_access` 兜底（学生只能操作「自己有权」即个人级本人的 kb）。分块修改（C2）**建议仅 admin/teacher**（学生不改切片内容），路由维持现状。
- **Q2 上传文档到 kb 的权限粒度**：能「访问」某 kb 就能往里传，还是更严？
  - **推荐**：`can_access` 通过即可上传。即同校教师可往班级级/学校级 kb 传；归属老师可往学生个人 kb 传；学生仅往自己个人 kb 传。
- **Q3 删除/修改文档的权限**：能访问即可删，还是限制上传者/owner/admin？
  - **推荐**：删除文档要求 `can_access` 通过 **且**（`doc.user_id == principal.user_id` 或 admin 或 kb.owner）。避免同校教师互相误删。`can_access` 是底线（防跨校/跨班），owner 校验是友军防误操作。
- **Q4 列表默认范围**：`GET /rag/document/list`（不带 kb_id）返回什么？
  - **推荐**：返回「当前主体可见的所有 kb 下的文档」（按 §6.2 的子查询过滤），而不是全量。

> 上述 4 项确认后，仅影响 §6 的判定细节，数据模型与框架均不动。

## 5. 要不要进一步抽象（架构判断）

> 用户原问：「是不是需要将鉴权功能抽象出来？」

**结论：框架层不动；业务层加一个『从属资源间接鉴权』小工具即可。等律师产品落地（第二用例）再把工具提升进框架。**

### 5.1 框架层（`common/aspect/resource_scope.py`）—— 不改

`Principal / ScopePolicy / ScopeRegistry / ViewerDependency` 已经是领域无关的通用机制，文档/分块直接复用，无需任何改动。强行加「从属资源」概念属于在只有 1 个产品时把抽象焊死（《知识库权限控制设计方案 §9.6》的 Rule of Three 原则），抽象错位风险大于收益。

### 5.2 业务层（`module_rag`）—— 加工具，不新建 Policy

在 `kb_scope_policy.py` 或新建 `module_rag/service/rag_access.py` 里，提供两个业务侧辅助：

```python
# 伪代码（本方案不改代码，仅示意）
async def assert_kb_accessible(db, kb_id, principal) -> RagKnowledgeBase:
    """取 kb 并校验可见；不可见抛 PermissionException。供 upload/list-by-kb 等用。"""
    kb = await KnowledgeBaseDao.get_by_id(db, kb_id)
    if kb is None or not KbScopePolicy().can_access(principal, kb):
        raise PermissionException(message='无权访问该知识库')
    return kb


async def assert_doc_accessible(db, doc_id, principal) -> RagDocument:
    """doc → kb → can_access。供 download/preview/delete 用。"""
    doc = await DocumentDao.get_by_id(db, doc_id)
    if doc is None:
        raise ServiceException(message='文档不存在')
    await assert_kb_accessible(db, doc.kb_id, principal)
    return doc


def doc_visible_subquery(principal, kb_model=RagKnowledgeBase):
    """生成「doc.kb_id IN (可见 kb 子查询)」的 where 条件，供文档列表过滤。"""
    cond = KbScopePolicy().visible_filter(principal, kb_model)
    return RagDocument.kb_id.in_(
        select(kb_model.kb_id).where(kb_model.del_flag == '0', cond)
    )
```

`chunk` 同理（`assert_chunk_accessible` 走 `chunk.kb_id`；`chunk` 列表入口是按 doc_id，先 `assert_doc_accessible` 再分页）。

### 5.3 何时提升进框架

当律师产品（律所-律师-当事人）出现「文档隶属于案件、案件有可见性」这类**第二个从属资源用例**时，再把 `assert_child_accessible(parent_policy, child→parent_id 解析器)` 提升为 `common/aspect/resource_scope.py` 的一等公民。届时形态已被两个用例验证，不会返工。

## 6. 实现指引（确认决策后执行，本期不改代码）

### 6.1 改造总原则

每个端点：**注入 `principal` → 传给 service → service 内做 can_access/子查询过滤**。controller 仍只做参数接收 + 响应封装，鉴权下沉到 service（与知识库 controller 风格一致）。

### 6.2 文档列表过滤（D1/D2）

`DocumentService.get_doc_list` 增 `principal` 参数：

```python
@classmethod
async def get_doc_list(cls, db, kb_id: int | None, principal: KbPrincipal):
    if kb_id is not None:
        # D2：先校验该 kb 可见，再取其下文档
        await assert_kb_accessible(db, kb_id, principal)
        return await DocumentDao.get_by_kb_id(db, kb_id)
    # D1：返回所有可见 kb 下的文档（子查询借 kb 的 visible_filter）
    cond = doc_visible_subquery(principal)
    return await DocumentDao.get_visible_list(db, cond)
```

DAO 增：

```python
@classmethod
async def get_visible_list(cls, db, cond: ColumnElement) -> list[RagDocument]:
    result = await db.execute(
        select(RagDocument)
        .where(RagDocument.del_flag == '0', cond)
        .order_by(RagDocument.create_time.desc())
    )
    return list(result.scalars().all())
```

### 6.5 删除（D6，叠加 Q3 的 owner 校验）

```python
@classmethod
async def delete_documents(cls, db, doc_ids, principal: KbPrincipal):
    for doc_id in doc_ids:
        doc = await assert_doc_accessible(db, doc_id, principal)
        # Q3：非上传者、非 admin、非 kb.owner → 拒绝
        kb = await KnowledgeBaseDao.get_by_id(db, doc.kb_id)
        if not (principal.is_admin
                or doc.user_id == principal.user_id
                or kb.owner_user_id == principal.user_id):
            raise PermissionException(message='无权删除他人文档')
        ...  # MinIO 删除 + 逻辑删除 + doc_count-1 不变
```

## 10. 一句话总结

文档与分块是知识库的从属资源，可见性继承自所属 kb；**复用已落地的 `ViewerDependency('rag.knowledge_base')` 与 `KbScopePolicy.can_access`，无需新建 Policy、无需动框架、无需改数据库**。要补的只是业务层一个「doc/chunk → kb_id → can_access」的间接判定工具（单条用 `assert_*`，列表用子查询借 `visible_filter`）。等律师产品出现第二个从属资源用例，再把该工具提升进框架。
