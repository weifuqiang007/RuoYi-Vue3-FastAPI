# 传输加密中间件：性能排查与公网部署决策

> 编写日期：2026-06-23
> 适用范围：`TransportCryptoMiddleware`（传输层请求解密 / 响应加密中间件）的性能诊断、是否启用的安全决策、以及未来重新启用的改造方案。
> 触发问题：`GET /dev-api/learning/activity/recent` 等鉴权接口在页面上耗时 1.7~2.3s，体感卡顿。

---

## 0. TL;DR（先看结论）

- 接口慢的**唯一根因**是 `TransportCryptoMiddleware`：每个加密请求它自身固定开销 0.7s，最重的 `activity/recent` 达 1.4s，占总耗时 66%~75%。
- 业务代码（4 个 DAO 查询 0.17s）、鉴权查库（0.13s）、Redis 缓存机制**全部无辜**。
- **当前决策：关闭应用层加密**（`transport_crypto_mode='off'`）。接口耗时将从 2.1s 降到 ~0.3s。
- **关键安全认知**：应用层加密**不是 HTTPS 的替代品**。它只加密请求体，加密不了 `Authorization` 头里的 JWT，在裸 HTTP 下防不住会话劫持。所以"开着它 = 又慢又没真安全"。
- **未来规划**：等有预算，前置 nginx + 域名 + Let's Encrypt 免费 HTTPS。TLS 就位后，应用层加密彻底无用武之地。若确有防爬需求再以正确姿势重开（见附录）。

---

## 1. 问题现象

页面刷新时，多个鉴权接口明显偏慢（浏览器 Network 实测）：

| 接口 | 页面实测耗时 |
|---|---|
| `GET /getInfo` | ~0.95s |
| `GET /getRouters` | ~1.05s |
| `GET /learning/task/student/list` | ~1.74s |
| `GET /learning/activity/recent` | ~2.1s |

而非鉴权的 `GET /transport/crypto/frontend-config` 仅 ~0.02s。**"鉴权接口普遍慢、非鉴权接口飞快"** 是第一线索——慢的环节出在鉴权链路上，而非业务查询。

---

## 2. 排查方法论（可复用）

采用**分层埋点 + 时间差反推**，逐层剥离耗时。核心是理解 FastAPI/Starlette 中间件的**洋葱模型**：

> `app.add_middleware()` 每次都把中间件插到**最前面**，因此**后注册 = 更外层**。
> 本次注册顺序（见 `middlewares/handle.py`）：
> context_cleanup → cors → gzip → response_header → trace → transport_crypto → **timing（最后注册=最外层）**

所以洋葱从外到内是：`timing → transport_crypto → trace → ... → endpoint`。

### 2.1 埋了三层计时

| 埋点 | 位置 | 测的是什么 |
|---|---|---|
| `[timing] ... backend X.XXXs` | `middlewares/timing_middleware.py`（最外层） | 后端**总**耗时（含 TransportCrypto） |
| `[timing] ... trace-downstream X.XXXs` | `middlewares/trace_middleware/middle.py` | TransportCrypto **内部**往下全部耗时（**不含** TransportCrypto 自身） |
| `[auth] ...` / `[activity/recent] ...` | `login_service.py` / `user_dao.py` / `activity_service.py` | 鉴权与业务各子步骤 |

### 2.2 关键公式

```
[timing] backend  −  [timing] trace-downstream  =  TransportCrypto 自身开销
```

因为 `timing` 包住 `transport_crypto`，`trace` 在 `transport_crypto` 内部。两者的差值，就是 TransportCrypto 的"解密请求 + 加密响应"自身耗时，**与下游业务/鉴权无关**。

> 注意一个坑：本项目的 `utils/log_util.logger`（loguru）**不支持 `%` 风格格式化**，只认 `{}` / f-string；要打 `%.4fs` 这类带值日志，必须用标准库 `logging.getLogger(...)`（会被 loguru 拦截接管，且支持 `%`）。排查时曾因此打印出字面量 `%.4fs`，已记录。

## 3. 关键证据（差值表）

| 接口 | backend | trace-downstream | **TransportCrypto 自身开销** | 占比 |
|---|---|---|---|---|
| `/transport/crypto/frontend-config`（明文透传） | 0.230s | 0.226s | **0.004s** | 2% |
| `/getInfo` | 0.937s | 0.233s | **0.704s** | 75% |
| `/getRouters` | 1.046s | 0.338s | **0.708s** | 68% |
| `/learning/task/student/list` | 1.740s | 0.973s | **0.767s** | 44% |
| **`/learning/activity/recent`** | **2.111s** | 0.720s | **1.391s** | **66%** |

**天然对照实验**：`frontend-config` 走的是明文透传分支（`transport_crypto_middleware.py:89-98`），只花 0.004s；一旦请求被加密，每个请求固定多花 0.7s，`activity/recent` 翻倍到 1.4s。**根因 100% 锁定在传输加解密中间件。**

---

## 4. 根因（代码层面两个硬伤）

### 4.1 每个请求都重新解析 RSA 私钥 PEM

`utils/transport_crypto_util.py:442`（`TransportCryptoUtil.decrypt_request_key`）：

```python
private_key = serialization.load_pem_private_key(private_key_pem.encode('utf-8'), password=None)
```

私钥对象本应在**进程启动时解析一次、缓存复用**，这里却在**每个加密请求**都重新 parse 一遍 PEM。这是一次同步 CPU 操作，直接占住事件循环线程。

### 4.2 每个加密请求额外 3 次 Redis 监控写入，串在请求关键路径上

`middlewares/transport_crypto_middleware.py`：

- `:104` `record_encrypted_request` → Redis pipeline
- `:105` `record_decrypt_success` → Redis pipeline
- `:373` `record_encrypted_response` → Redis pipeline（响应阶段）

这三处都是 `await` 的 Redis 往返，本应 fire-and-forget，却卡在请求关键路径里，放大延迟。

### 4.3 为什么 `activity/recent` 是别人的 2 倍（1.4s vs 0.7s）

页面刷新时 `getInfo / getRouters / activity/recent / task/list` **同时并发**，而这些同步加密操作（PEM 解析 + RSA + AES）**全挤在单线程事件循环上串行执行**。排得越靠后的请求，等事件循环的时间越长，wall-clock 被放大。这是典型的"同步阻塞型 crypto 把并发打回串行"。

> 推论：单接口压测时开销可能不到 0.2s；只有**并发**才会膨胀到 0.7s+。排查时若只单测一个接口容易误判。

## 5. 决策分析：A 关闭 vs B 保留并修好

### 5.1 最关键的安全认知（决定性因素）

**应用层加密不是 HTTPS 的替代品。** 它只加密请求体 / query 的 `__enc` 信封，**加密不了 HTTP 头**。而 JWT token 放在 `Authorization: Bearer xxx` 请求头里。

→ 在**裸 HTTP** 下开着它：登录密码在 body 里被护住 ✓，但每个请求头里的 **JWT 明文暴露** → 中间人抓包即可会话劫持 ✗。

**结论：开着它 ≠ 安全。对裸 HTTP 的 demo，它是"又慢、又不真安全"的最差组合。**

### 5.2 A / B 对比

| 维度 | HTTPS (TLS) | 本项目应用层加密 |
|---|---|---|
| 保密范围 | 整条通道（URL+头+体） | **仅请求体**（头明文） |
| 完整性 / 防篡改 | ✓ | ✓ |
| 防重放 | ✓ TLS record 层自带 | ✓（靠 Redis，每请求一次） |
| 性能开销 | 硬件加速，微秒级 | **0.7~1.4s/请求** |
| 标准化 | 行业标准 | 自研 |

### 5.3 B 真正有价值的场景（本项目基本都不沾）

1. 防爬 / 防脱离浏览器脚本化刷接口（教学系统一般无所谓）；
2. 不可信的反代跳链（nginx 终止 TLS 后到后端那段明文，且不信任该链路——自服务器自跳通常可信）；
3. 合规硬性要求必须"应用层加密"打钩（教学系统无此要求）。

即便命中，也得**先把性能修好**才能上，否则 1.4s/请求照样不能见人。

## 6. 最终方案与未来规划

### 6.1 当前（纯 IP、零成本、demo 阶段）—— 选 A

1. 配置关闭应用层加密：`transport_crypto_mode='off'`（或 `transport_crypto_enabled=False`）。
   - 前端 `/transport/crypto/frontend-config` 会下发 `transportCryptoActive=false`，前端自动停止加密，无需改前端。
   - `activity/recent` 预期从 2.1s → ~0.3s。
2. 清理本次排查的临时埋点（见第 7 节清单）。
3. 公网裸 IP 跑，nginx 反代到后端（不挂证书）；挂上**基础防护**：限流、登录失败锁定、关闭调试模式。这些才是 demo 公网暴露时真正该担心的（防脚本扫描，而非 MITM）。
4. demo 数据用测试数据，不放真实敏感信息；管理员账号用强口令。

### 6.2 有预算后 —— 上 HTTPS（一步到位）

- 买个便宜域名指向该 IP，用 **Let's Encrypt 签免费证书**（证书本身免费，花钱的只是域名，几块到几十块）。
- 前置 nginx/caddy + TLS。
- TLS 就位后整条链路被兜底，应用层加密彻底无用武之地，**保持关闭**即可。

> 坑提示：Let's Encrypt **不给裸 IP 签证书**。纯 IP 只能自签 → 浏览器大红警告，UX 和"安全感"双输。所以"上 HTTPS"天然等价于"先上域名"。

### 6.3 折中选项（零成本，若连"登录密码明文过公网"都不想接受）

只让 `/login` 走加密、其余全明文：登录那一下付一次性 1.4s，之后所有请求都快。

配置思路：`transport_crypto_required_paths=/login`，其余路径 optional。**前置依赖**：需确认前端 `src/utils/transportCryptoPolicy.js` 在 optional 模式下是"只加密 required 路径"而非"全加密"——本结论尚未验证，落地前必须先读前端策略。对简单 demo，建议直接走 6.1，折中选项等真介意了再说。

## 附录 A：将来若选 B（保留加密），具体怎么改

按性能影响从大到小：

1. **缓存私钥对象**：`TransportKeyProvider` 启动时把每个 kid 的私钥 `load_pem_private_key` 一次，存进 `TransportKeyPair`（新增 `private_key` 字段）；`decrypt_request_key` 直接复用对象，删掉每请求的 `load_pem_private_key`。预期消除大部分固定开销。
2. **监控写入移出请求路径**：3 处 `TransportCryptoMonitorUtil.record_*` 改为 `asyncio.create_task(...)` fire-and-forget，或用 `BackgroundTasks`，或进程内计数批量 flush。不要让 Redis 往返阻塞响应。
3. **crypto 丢线程池**：`decrypt_envelope` / `encrypt_response_body` 包一层 `await asyncio.to_thread(...)` 或 `loop.run_in_executor(...)`，避免同步 RSA/AES 占住事件循环、避免并发串行化。
4. （可选）`validate_replay` 的 Redis `SET NX` 保留——这个本身不慢，且是安全语义，不动。

完成 1+2+3 后，单请求加密开销预计可压到个位数毫秒，并发不再放大。
