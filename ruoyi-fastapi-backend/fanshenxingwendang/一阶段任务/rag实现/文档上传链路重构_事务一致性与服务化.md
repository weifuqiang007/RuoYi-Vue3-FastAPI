## 一、背景：上传接口遗留的 5 个问题

初版 `document_controller.upload_document` 把 MinIO 上传、DB 写入、解析触发全部堆在 controller 里，并在代码注释中提出了 5 个疑问。本文档记录这次重构对这 5 个问题的诊断与最终解决方案。

| # | 问题 | 严重程度 |
|---|------|---------|
| 1 | 要不要开事务？上传成功但解析失败时用户无法下载 | 高（数据一致性） |
| 2 | 为什么业务逻辑写在 controller 而不是 service？ | 中（架构规范） |
| 3 | 上传后 `rag_knowledge_base.doc_count` 没有加 1 | 中（统计错误） |
| 4 | MinIO 报错时前端收到什么提示？ | 中（用户体验） |
| 5 | MinIO 桶是什么？存哪？为什么本地客户端找不到？ | 高（排查阻塞） |

## 二、关键发现（重构前必须先厘清的事实）

### 2.1 项目本来就有事务，且粒度是"一个请求一个事务"

看 `config/get_db.py`：

```python
async def get_db():
    async with AsyncSessionLocal() as current_db:
        try:
            yield current_db
            await current_db.commit()      # 请求结束统一 commit
        except Exception:
            await current_db.rollback()    # 任何异常统一 rollback
            raise
```

而所有 DAO（`DocumentDao.create`、`update_status`、`ChunkDao.bulk_insert` 等）用的都是 `flush()`，不是 `commit()`。

**结论：一个请求内的所有 DB 操作天然在同一个事务里。** 真正的问题不是"没开事务"，而是 **MinIO（外部系统）与 DB 之间无法跨系统事务**。

### 2.2 初版失败路径的真实表现

```
minio.put 成功 → DocumentDao.create(flush) → process_document 解析失败
                                                  │
                                                  ▼ process_document 内部 raise
                                  get_db except → 整笔事务 rollback
                                                  │
                                  ┌───────────────┴───────────────┐
                                  ▼                                ▼
                      DB 记录被回滚（列表看不到）        MinIO 文件残留（孤儿）
```

所以"用户无法下载"的本质是：**DB 记录被回滚没了，而 MinIO 文件成了垃圾**。

### 2.3 MinIO 配置默认指向远程（问题 5 的根因）

| 配置项 | 值 | 来源 |
|--------|-----|------|
| `ACTIVE_PROFILE` | `'test'` | `config/env.py:16` |
| `MINIO_HOST` | `115.220.6.150:29000` | `.env.test:185` |
| `MINIO_BUCKET` | `rag` | `.env.test:191` |

应用默认加载 `.env.test`，所以**文件实际传到了远程 `115.220.6.150:29000`，而非本地 `127.0.0.1:9000`**。用本地 MinIO 客户端自然找不到 `rag` 桶和文件。

另外，`MinioClient` 是懒加载单例，桶只在**第一次** `get_instance()`（即第一次上传/下载）时才创建，应用启动时不建桶。

### 2.4 MinIO 错误并非静默，但提示质量差

`minio.put` 失败重试 3 次后抛 `RuntimeError("MinIO: 上传失败，已重试3次 ...")`，冒到全局异常处理器：

```python
@app.exception_handler(Exception)
async def exception_handler(request, exc):
    logger.exception(exc)
    return ResponseUtil.error(msg=str(exc))   # 把裸异常字符串回给前端
```

前端**会**收到 `{code: 500, msg: "MinIO: 上传失败，已重试3次 ...", success: false}` 并弹提示，但看到的是内部堆栈字符串，体验差。

## 三、设计决策（已与需求方对齐）

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 解析/向量化失败如何处理 | **保留文档记录 + 标记失败**（`parse_status='9'`/`embed_status='9'`），上传接口仍返回成功 | 符合 RAGFlow 状态机思路，复用现有状态字段，用户可在列表看到失败文档并重试；一次偶发解析错误不丢整个上传 |
| 重构范围 | **全部接口统一服务化** | 所有 MinIO 调用与业务逻辑下沉到 `DocumentService`，controller 全部变薄，与 `knowledge_base_controller` 规范一致 |

## 五、核心实现

### 5.1 doc_count 原子自增（DAO 层）

用 SQL 表达式自增，避免"读出来 +1 再写回"的并发问题：

```python
# module_rag/dao/knowledge_base_dao.py
@classmethod
async def increment_doc_count(cls, db: AsyncSession, kb_id: int, delta: int = 1):
    await db.execute(
        update(RagKnowledgeBase)
        .where(RagKnowledgeBase.kb_id == kb_id)
        .values(doc_count=RagKnowledgeBase.doc_count + delta)
    )
```

### 5.2 上传主流程：三层一致性（Service 层）

```python
# module_rag/service/document_service.py
@classmethod
async def upload_document(cls, db, kb_id, file, user_id) -> RagDocument:
    content = await file.read()
    file_type = os.path.splitext(file.filename)[1].lower()
    object_name = f"rag/{kb_id}/{uuid.uuid4().hex}{file_type}"
    minio = MinioClient.get_instance()

    # ① 入库前：上传 MinIO —— 失败抛 ServiceException（前端友好），无 DB 脏数据
    try:
        minio.put(object_name, content)
    except Exception as e:
        logger.error(f"MinIO 上传失败 kb_id={kb_id}: {e}")
        raise ServiceException(message="文件存储失败，请稍后重试")

    # ② 入库（同一事务）：建记录 + doc_count+1 —— 失败补偿删 MinIO 文件（无孤儿）
    doc = RagDocument(kb_id=kb_id, doc_name=file.filename, file_path=object_name,
                      file_type=file_type, file_size=len(content), user_id=user_id)
    try:
        doc = await DocumentDao.create(db, doc)
        await KnowledgeBaseDao.increment_doc_count(db, kb_id, 1)
    except Exception as e:
        logger.error(f"文档记录保存失败，回滚 MinIO 文件 {object_name}: {e}")
        minio.remove(object_name)
        raise ServiceException(message="文档保存失败，请稍后重试")

    # ③ 处理（尽力而为，失败不抛出，仅记录状态）
    await cls.process_document(db, doc.doc_id)
    return doc
```

**三层一致性保证：**

| 阶段 | 失败处理 | 结果 |
|------|---------|------|
| MinIO 上传 | 抛 ServiceException | 无 DB 脏数据 |
| DB 写入 | 补偿删 MinIO 文件 + 抛 ServiceException | 无孤儿文件 |
| 解析/向量化 | 标记状态，不抛出 | 保留记录供重试 |

### 5.3 解析失败保留记录（process_document 改造）

去掉 `except` 里的 `raise`，失败状态落库后正常返回：

```python
except Exception as e:
    logger.error(f"文档 {doc_id}: 处理失败 - {e}")
    # 失败状态落库后正常返回，不抛出 —— 保留文档记录供用户重试
    await DocumentDao.update_status(
        db, doc_id, parse_status="9", embed_status="9", error_msg=str(e)[:500]
    )
```

### 5.4 重试幂等性（重要副作用修复）

> 初版 `process_document` 失败会 `raise`，`get_db` 回滚掉半成品分块。
> 改成"保留记录 + 可重试"后，重试会导致**分块重复累积**。

因此在 `process_document` 开头清理旧分块，保证重新解析幂等：

```python
# module_rag/dao/chunk_dao.py
@classmethod
async def delete_by_doc_id(cls, db, doc_id):
    await db.execute(
        update(RagChunk).where(RagChunk.doc_id == doc_id, RagChunk.del_flag == '0').values(del_flag='2')
    )

# module_rag/service/document_service.py —— process_document 开头
await ChunkDao.delete_by_doc_id(db, doc_id)   # 重试场景保证幂等
```

### 5.5 controller 变薄

```python
# module_rag/controller/document_controller.py
@staticmethod
@document_controller.post('/upload/{kb_id}', summary='上传文档到知识库')
async def upload_document(kb_id, file, query_db, current_user):
    doc = await DocumentService.upload_document(query_db, kb_id, file, current_user.user.user_id)
    return ResponseUtil.success(data={
        'doc_id': doc.doc_id, 'file_path': doc.file_path,
        'parse_status': doc.parse_status, 'embed_status': doc.embed_status,
    })
```

download / preview / delete 同理：controller 只调 service + 包响应，HTTP 构造（StreamingResponse）留在 controller。

### 5.6 启动预热 MinIO（server.py）

```python
def _init_minio() -> None:
    try:
        MinioClient.get_instance()
        logger.info('MinIO: 启动初始化完成')
    except Exception as e:
        logger.warning(f'MinIO: 启动初始化失败（RAG 文件功能将不可用）：{e}')
```

MinIO 是 RAG 模块依赖，连接失败**不应阻断整个应用启动**，仅记录警告；真正使用时仍会再次连接并在失败时抛友好错误。

## 六、5 个问题的最终解决方案对照

| # | 问题 | 解决方案 |
|---|------|---------|
| 1 | 事务 | 项目本就一个请求一个事务。补三层一致性：MinIO 上传失败→友好错误无脏数据；DB 写失败→补偿删 MinIO 文件无孤儿；解析失败→不回滚、标记 `status='9'`、保留记录可重试 |
| 2 | controller vs service | 全部业务逻辑下沉到 `DocumentService`，controller 只做参数接收 + 调 service + 包响应，与 `knowledge_base_controller` 一致 |
| 3 | doc_count | `increment_doc_count` 原子自增，上传 +1、删除 -1（删除只对未删文档减，防重复） |
| 4 | MinIO 报错 | 转成 `ServiceException(message="文件存储失败，请稍后重试")`，前端友好提示，详细堆栈进服务端日志 |
| 5 | 找不到桶 | 诊断结论：默认 `test` 环境 `MINIO_HOST=115.220.6.150:29000`（远程），文件在那台机器；启动预热让桶尽早创建、连接问题尽早暴露 |

## 七、一致性状态机（文档全生命周期）

```
              upload_document
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
   MinIO失败    DB失败        DB成功
   ServiceException  补偿删MinIO    │
   (无脏数据)    ServiceException   │
   (无孤儿)                  process_document
                              │
                 ┌────────────┼────────────┐
                 ▼            ▼            ▼
             parse失败    embed失败    全部成功
             status='9'   status='9'   status='2'
             (保留记录)   (保留记录)   (可检索)
                 │            │
                 └───用户可重试(reparse)───┘
```

状态字段：`parse_status` / `embed_status`
- `0` 待处理 → `1` 进行中 → `2` 完成 / `9` 失败

## 八、验证清单

1. **正常流程**：建知识库 → 上传正常 PDF → 列表确认 `doc_count=1`、`parse_status`/`embed_status` 流转到 `2`。
2. **解析失败**：上传损坏/不可解析文件 → 确认**上传接口返回成功**、列表里该文档 `embed_status='9'`、`error_msg` 有内容、`doc_count` 仍 +1。
3. **下载**：下载刚上传的文档 → 正常下载（验证 DB 记录未被回滚）。
4. **删除**：删除文档 → 确认 `doc_count` 减 1、MinIO 文件被删。
5. **MinIO 错误路径**：临时改 `MINIO_HOST` 为错误地址重启 → 上传收到友好提示"文件存储失败，请稍后重试"，服务端日志有详细堆栈，DB 无脏记录。
6. **孤儿清理**：模拟 DB 写入失败 → 确认 MinIO 中未留下孤儿文件。
7. **重试幂等**：对失败文档重新解析 → 确认分块不重复累积。
8. **MinIO 实例确认**：连远程 `115.220.6.150:29000`（账号 `minioadmin/minioadmin`）确认 `rag` 桶与文件存在；或切 `--env dev` 在本地复测。

| `reparse` 重新解析接口 | 架构文档原计划有 `POST /rag/doc/reparse/{doc_id}`，目前失败文档没有前端"重试"入口；幂等逻辑已就绪，加一个调 `process_document` 的接口即可 |
