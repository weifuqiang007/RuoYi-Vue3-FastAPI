## 二、RAG 的「模式」全景（你问"都有哪些模式"）

RAG 不是一项技术，是一组可插拔的模块。学术界把它分成三代演进，每一代里又有具体技术模式。先建立地图，再决定走到哪。

### 2.1 三代演进范式

```
Naive RAG（你现在在这里）
  Index: 解析→固定分块→embedding→存
  Query: query→向量召回 top-k→拼 prompt→生成
  问题：召回不准、长尾丢、无法溯源、模型幻觉

        ↓ 在 retrieve 前后加优化

Advanced RAG（下一步目标）
  Pre-retrieval:  query 改写 / 路由 / 分解
  Retrieval:      向量 + 关键词 混合 + RRF
  Post-retrieval: rerank 精排 + 阈值过滤 + 去重 + 压缩

        ↓ 引入反思与模块化

Modular RAG（高级）
  可插拔模块 + Self-RAG/CRAG（模型自己判断要不要检索、检索够不够）+ 多跳检索
```

### 2.2 各阶段可选的技术模式（标★的是你下一步该上的）

| 阶段 | 模式 | 解决什么 | 你的现状 | 建议 |
|---|---|---|---|---|
| **解析** | 纯文本抽取 | 基础 | ✓ PyMuPDF | 保留 |
| | 版面识别（DeepDoc/OCR） | 复杂 PDF / 扫描件 / 表格 | ✗ 跳过非文字块 | 复杂文档再上，或调 RAGFlow 兜底 |
| **分块** | 固定窗口 | 基础 | ✓ FixedChunker | 保留但加标题前缀 |
| | ★ 按结构（标题/章节）分块 | 章节语义完整 | ✗ | **上**：见 §四 |
| | 语义分块 | 语义边界对齐 | ✗ | 可选 |
| | Parent-Child（小块检索、大块给模型） | 召回准 + 上下文足 | ✗ | 进阶 |
| **向量化** | Dense embedding | 语义相似 | ✓ embedding-3 | 保留 |
| | Sparse（BM25/SPLADE） | 关键词/专有名词精准命中 | △ 但中文分词废了 | **修中文分词** |
| **Pre-retrieval** | ★ Query 改写（HyDE/扩写） | 学生口语化提问→专业 query | ✗ | **上**：反思区特别有用 |
| | Query 路由 | 不同问题去不同库 | ✗ | 多库后再上 |
| **Retrieval** | ★ 混合检索（向量+关键词+RRF） | 召回互补 | △ 结构在，中文路废 | **修中文分词** |
| **Post-retrieval** | ★★ Rerank（cross-encoder） | 精排，提准的最大杠杆 | ✗ | **必上**：见 §五 |
| | ★ 相似度阈值 + 去重 | 过滤不相关 | ✗ | **上** |
| | 上下文压缩 | 去冗余 | ✗ | 可选 |
| **Generation** | ★ Citation/溯源 | 可信、可核查 | ✗ | **上**：见 §三 |
| | Self-RAG / CRAG | 模型自查检索质量 | ✗ | 进阶 |

> **关键认知**：在中文教育知识库这种"文档相对规整、问法口语化、要求可信"的场景里，投入产出比最高的三件事是 **①rerank ②标题上下文 ③citation**，而不是换更大的 embedding 模型。

### 2.3 你当前的位置 vs 推荐目标

```
当前：  Naive RAG，且关键词路失效 ≈ 纯向量 Naive RAG
第一步：Advanced RAG（修中文分词 + rerank + 阈值 + 标题上下文 + 清洗）   ← 二阶段主目标
第二步：加 Query 改写 + Citation 完整闭环 + parent-child
第三步：Modular RAG（路由 / Self-RAG），按需
```

## 三、溯源（Citation）设计（你问"我还希望进行溯源"）

溯源 = 回答里的每一句论断，都能追回到"哪份文档、第几页、哪一段原文"。分四层做，**缺一层就断**：

### 3.1 存得下：chunk 表 metadata 富化

当前 metadata 只有 `{page, type}`（`document_service.py:170`），且 DOCX/TXT 的 page 恒为 0。补成：

```python
metadata = {
    "doc_id": doc_id,
    "doc_name": doc.doc_name,          # 冗余，避免每次 join
    "file_type": doc.file_type,
    "page": block.get("page"),          # PDF 真实页码
    "heading_path": ["第一章 概述", "1.2 定义"],  # 章节面包屑
    "char_start": 1234,                 # 在文档纯文本中的字符偏移
    "char_end": 1580,
    "chunk_index": i,                   # 文档内顺序
}
```

- `heading_path`：解析时维护一个"标题栈"，遇到 title 就 push/replace，每个 chunk 记录当前栈快照。
- `char_start/char_end`：解析后把整篇文本拼起来，记录每个 chunk 的偏移，可精确高亮定位（解决 DOCX/TXT 没有页码的问题）。

### 3.2 取得出：检索结果透出 metadata

`controller/retrieval_controller.py:60-65` 现在丢掉了 metadata。改成在响应里带上 `doc_name / page / heading_path / chunk_id / score`，前端就能渲染引用卡片。

### 3.3 用得上：prompt 要求模型标注引用

system prompt 里明确约束：

```
你必须基于【参考资料】回答。每一段论断末尾用 [1][2] 标注引用了哪条资料（编号对应参考资料序号）。
若参考资料不足以回答，直接说明，不得编造。回答末尾输出 JSON：{"citations": [{"id":1, "chunk_id": "..."}]}
```

模型输出自带 `[1]`，前端把 `[1]` 渲染成可点击、点击展开原文片段 → 完整溯源闭环。

### 3.4 看得见：前端引用交互

- 正文中 `[1]` → 悬浮显示 doc_name + page + 原文片段
- 点击 → 跳转文档原文（PDF 按 page，DOCX/TXT 按 char_offset 滚动高亮）

> 你现在是四层**全断**（存得不全、取出丢掉、prompt 没要求、前端没展示）。优先做 3.1 + 3.2 + 3.3，3.4 前端后补。

## 四、数据清洗：到底清洗什么（你问"数据如何清洗"）

清洗不是一步，是**四个时机**各清一类。当前你一个都没做（`clean_text` 写了没人调）。

### 4.1 清洗的四个时机 × 各清什么

| 时机 | 清什么 | 具体规则 | 落点 |
|---|---|---|---|
| **① 上传前（文件级）** | 水印、页眉页脚、目录页 | PDF 抽取后剔除重复出现的页眉/页脚串；识别并丢弃目录页 | `parser/pdf_parser.py` 增强 |
| **② 解析后（文本级）** | 断行、乱码、HTML、多余空白、繁简 | 行尾无句末标点且下行非标题→合并断行（修 PDF 跨页切断）；去 HTML 标签；`\s+` 归一；可选繁→简 | 新增 `service/cleaner.py`，在 parser 输出后、chunker 前 |
| **③ 分块后（chunk 级）** | 短块、乱码块、重复块 | `len<20 字` 丢弃或并入相邻；中文字符占比过低且非外文→丢弃；精确 hash 去重 + 近似去重（余弦>0.95） | `chunker` 输出后、入库前 |
| **④ 向量化前（校验）** | 超长、空内容 | 超长截断到模型上限；空/纯空白跳过 | `embedding_service.embed_texts` 入口 |

### 4.2 接入位置（改一处就串起来）

在 `document_service.process_document` 里，在 `parser.parse` 之后、`chunker.chunk` 之前插一个清洗阶段：

```
解析 blocks → 【清洗①+②】 → 分块 → 【过滤③】 → 入库 → 【校验④】向量化
```

### 4.3 最小可用清洗规则（先上这套，立竿见影）

```python
# service/cleaner.py（新建）
import re, hashlib

def clean_block_text(text: str) -> str:
    text = re.sub(r'<[^>]+>', '', text)          # 去 HTML
    text = re.sub(r'[ \t]+', ' ', text)          # 归一空白
    text = re.sub(r'\n{3,}', '\n\n', text)       # 多空行归一
    # 合并断行：行尾不是句末标点，且下一行不是空行 → 拼回（修 PDF 跨页切断）
    text = re.sub(r'([^.!?。！？；;])\n([^\n])', r'\1\2', text)
    return text.strip()

def is_valid_chunk(content: str) -> bool:
    if len(content) < 20:                         # 太短
        return False
    chinese = sum(1 for c in content if '一' <= c <= '鿿')
    if 0 < len(content) and chinese / len(content) < 0.15 and not re.search(r'[a-zA-Z]{3,}', content):
        return False                              # 既非中文也非正常外文 → 乱码
    return True

def dedup_key(content: str) -> str:
    return hashlib.md5(content.strip().encode()).hexdigest()
```

然后在 `document_service` 里：清洗每个 block 文本 → chunk → 过滤 `is_valid_chunk` → 用 `dedup_key` 在本文档内去重。

# 社会学RAG项目：Markdown文档存储方案、策略与注意事项
## 提问
我现在接了一个社会学rag的项目。
我现在想要将markdown文档存储在rag中。
都有什么策略呢？
应该怎么存储呢？
或者说有什么需要注意的点呢？

## 完整解答
先点明核心特点：**社会学文本和普通技术文档完全不一样**
大量长段落论述、引用文献、访谈笔录、案例、脚注、层级标题、表格、观点辨析、多章节逻辑关联；Markdown自带标题层级、列表、引用块、分割线，天然具备语义结构。
如果粗暴按固定字符切分，极易切断论证链条，检索出来碎片化观点，造成**断章取义**（社会学RAG头号坑）。

下面分：存储架构方案 → 切分策略（最重要） → 元数据设计 → 入库方式 → 社会学特有避坑点。

## 一、Markdown 在RAG系统里有几种主流存储策略
### 方案1：原始MD原文存对象存储 + 向量库只存切片（推荐生产首选）
架构：
1. 对象存储：MinIO / S3 / 本地文件库 / SQLite
   保存**完整原始markdown文件**，保留全部格式：标题、#层级、>引用、表格、链接、脚注
2. 向量数据库（pgvector/chroma/qdrant/weaviate）
   只保存：文本切片 + 向量 + 丰富元数据
3. 检索链路：
   向量召回切片 → 通过元数据路径定位原始MD → 拉取原文，支持上下文扩展、溯源页码/章节

✅ 优势
- 向量库轻量化，不膨胀；随时可以重新调整切分规则、重新向量化
- 支持溯源：回答输出时可以标注「出自《xxx》第三章，原始文档位置」，社会学论文非常看重来源溯源
- 原始MD永久保存，后续可以微调解析规则重做知识库

❌ 代价：需要维护一套文件索引，元数据必须记录文件唯一ID、路径。

### 方案2：向量库同时存【切片文本+完整MD原文】（原型、快速开发首选）
向量库每条向量记录内携带两个字段：
`chunk_text`（向量化文本） + `full_md`（完整文档字符串）
适合Demo、内部小知识库，不用额外搭建对象存储。

⚠️ 缺陷：
文档量大后极度浪费存储空间；更新文档时全量更新多条chunk；**不适合上千份以上社会学文献**。

### 方案3：结构化解析MD，拆成层级文档存入知识库（社会学最优进阶方案）
利用Markdown标题层级 `# ## ###` 做**语义天然边界**
把一份MD文档解析成树结构：
```
# 第一章 城市化理论
## 1.1 齐美尔城市社会学
### 1.1.1 大都市与精神生活
段落、访谈资料、引用文献...
```
每一个二级/三级标题节点作为基础单元，再进行微调切片。
> 社会学文献天然依靠章节划分论证单元，比固定长度滑动窗口强得多。

### 方案4：存入文档数据库（MongoDB/Postgres）做中间层
MD原文入库，附带解析后的目录树、标题索引；向量库只存切片。
适合需要**复杂筛选检索**场景：例如按作者、出版年份、研究地域、研究理论流派先过滤，再向量检索。

> 技术栈推荐（Python + FastAPI + pgvector）起步组合：
> Postgres（元数据+可选原始MD）+ pgvector（向量），小规模不用单独对象存储。

## 二、Markdown 解析 & Chunk切分【重中之重，社会学RAG核心】
禁止直接使用：固定大小滑动窗口（RecursiveCharacterTextSplitter 无脑默认参数）
典型灾难场景：
一段长达800字的社会学论证被拦腰切断；模型检索到后半段，缺失前提，得出扭曲结论。

### 推荐分层切分策略（适配Markdown）
#### 1）第一步：MD语法感知解析（必须做）
使用专用markdown解析器，不要当成纯文本读取
可选工具：
- `markdown-it-py` 解析成AST抽象语法树
- `langchain-markdown-splitter`
- LlamaIndex MarkdownNodeParser

解析时识别区块类型：
- 标题 Heading（# ~ ######）
- 正文段落 Paragraph
- 引用块 `>` （访谈记录、文献引文，社会学高频）
- 有序/无序列表
- 表格 Table（社会学问卷、统计表格，极易被切坏）
- 分割线、脚注、注释

#### 2）二级策略：**层级优先切分 + 少量滑动兜底**
执行顺序：
1. 按照 `## / ###` 标题进行**首次分割**，每个章节块作为基础单元
2. 判断单元长度：
   - 块 300～1200 token：直接作为一条chunk
   - 块 >1500 token：在段落边界做二次细分（优先段落结尾、句号，不要一句话切断）
   - 块 <150 token：向上合并到上级章节，避免碎片chunk

> 社会学推荐Chunk经验值（中文token）
> 基础长度：**600 token 为主，上限1200token**
> 重叠上下文（overlap）：**100～180 token**
> overlap不要太大，否则大量重复向量；也不能0，避免论证跨两个chunk断裂

#### 3）特殊区块单独规则（社会学特有）
1. **访谈笔录（> 引用块）**
多条连续访谈对话尽量保留完整，不要切割单条问答
2. **表格**
整张表格尽量不拆分；表格附带的分析文字和表格绑定在同一个chunk
3. **参考文献列表**
方案A：单独抽成一类chunk，打上元数据type=reference；检索时可以设置权重降低
方案B：直接过滤参考文献，不参与向量化（视业务需求）
4. **脚注**
将脚注内容合并到正文对应的段落，不要孤立存放

### 两种成熟开源实现参考
1. LangChain：`MarkdownHeaderTextSplitter` + `RecursiveCharacterTextSplitter` 组合
2. LlamaIndex：`MarkdownNodeParser`（原生AST解析md结构）

伪代码思路：
```python
# 1.先用标题分割md
header_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=[
    ("#", "h1"),
    ("##", "h2"),
    ("###", "h3")
])
md_sections = header_splitter.split_text(raw_md)
# 2.对过长章节再细切
sub_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=150,
    separators=["\n\n", "\n", "。", "，"]
)
```

## 三、元数据 Metadata 设计（社会学项目极其关键）
向量库每一条chunk必须携带元数据，用于**过滤、溯源、检索增强**。
基础字段建议：
```json
{
  "doc_id": "唯一文档uuid",
  "file_name": "城市化研究.md",
  "file_path": "知识库/城市社会学/",
  "title": "文档主标题",
  "current_section": "1.1 齐美尔大都市理论",
  "header_tree": ["# 城市社会学","## 现代性与都市人格"],
  "chunk_index": 23,
  "block_type": "paragraph|quote|table",
  "author": "",
  "year": "",
  "research_field": ["城市社会学","现代性理论"],
  "source_type": "学术论文|访谈实录|著作章节|调研报告",
  "tags": ["齐美尔","大都市","社会互动"]
}
```
使用场景：
用户提问：**齐美尔对于城市人际交往的观点**
可以先通过元数据筛选 `tags包含齐美尔`，再做向量检索，减少无关文本干扰。

## 四、落地存储完整方案选型
### 场景A：中小型知识库（<500份MD，内部项目，FastAPI+PG+pgvector）
> 最适合起步
1. Postgres主表：存储完整markdown原文、文档元数据、目录树
2. pgvector子表：存储chunk文本、embedding向量、chunk粒度元数据
✅ 优势：一套数据库搞定，运维简单；支持SQL条件过滤+向量混合查询

### 场景B：大规模知识库（上千份MD，持续新增更新）
1. MinIO/S3：存放原始.md文件
2. Postgres：文档索引、元数据管理
3. Qdrant / Weaviate：独立向量库，横向扩展

### 场景C：纯原型快速验证
LlamaIndex / LangChain + Chroma本地向量库，MD原文直接存入向量库metadata字段。
⚠️ 不要直接上生产。

## 五、社会学RAG + Markdown 专属大坑（重点注意）
### 1. 避免「语义割裂、断章取义」（第一风险）
社会学很多观点存在**正反辩论、前提条件、限定语境**。
单纯固定长度切分极易只拿到结论，丢失前提。
👉 对策：优先基于markdown章节边界切分，提高chunk上限，不要切太碎。

### 2. 引文、访谈记录处理不当
大量 `>` 访谈文本如果和分析文本拆开，模型分不清哪些是受访者原话、哪些是作者分析。
👉 解析时保留markdown标记或者在文本中做标识，不要直接删掉格式符号。

### 3. Markdown格式清洗误区
不要粗暴删除所有 `# > | -`
少量标记有助于模型识别文本结构；
但**不要把原始md全部符号扔进embedding**（过多符号干扰向量编码）。
建议策略：
- 向量化的chunk文本：保留标题文字，移除#符号；保留引用语义，可选择性保留>；
- 原始存档MD：完整保留一切格式，用于溯源展示。

### 4. 版本更新问题
后续修改某一份markdown怎么办？
策略：
采用**文档粒度失效机制**
当一份md更新 → 查询doc_id对应的所有chunk，批量删除 → 重新解析、切分、写入新向量
不建议增量局部修改chunk，复杂度极高。

### 5. 检索后上下文扩充（重要优化）
向量召回的只是单个chunk；社会学论证经常跨相邻chunk。
实现方案：
召回chunk后，根据 `doc_id + chunk_index`，向前后读取相邻1~2个chunk拼接再喂给LLM。

### 6. 区分一手资料/二手文献
访谈实录（一手）、学术综述（二手）、理论原著，建议用元数据区分；
可以在Prompt里设置权重，比如用户做实证研究优先召回访谈资料。

### 7. 表格数据丢失
Markdown表格经过简单文本分割很容易变成乱码文本。
解析阶段检测表格区块，完整保留表格markdown文本，禁止对半切割表格。

## 9.4 Markdown 专项：解析升级怎么做（P0 flagship）

**目标**：把 MD 解析从"纯文本+startswith('#')"升级为"结构感知"，输出带 `heading_path` 和 `block_type` 的 block 列表，喂给标题感知 chunker。

**三种实现选一种**（按你的"自己写每一层"偏好排序）：

| 方案 | 依赖 | 优点 | 缺点 |
|---|---|---|---|
| **A. 手写轻量解析器（推荐）** | 无 | 完全可控、符合学习目标、~60 行 | 需自己处理边界情况 |
| B. `markdown-it-py` → AST | markdown-it-py | 最精确、覆盖所有 MD 语法 | 多一个依赖、AST 遍历有学习成本 |
| C. LangChain `MarkdownHeaderTextSplitter` | langchain-text-splitters | 开箱即用、久经考验 | 黑盒、与"自己写"哲学相悖 |

**方案 A 的核心设计**（新建 [service/parser/markdown_parser.py](ruoyi-fastapi-backend/module_rag/service/parser/markdown_parser.py)，并在 [parser/__init__.py](ruoyi-fastapi-backend/module_rag/service/parser/__init__.py) 把 `.md` 指向它）：

```python
import re
from module_rag.utils.text_cleaner import find_codec

HEADING_RE = re.compile(r'^(#{1,6})\s+(.*)$')
LIST_RE = re.compile(r'^\s*([-*+]|\d+\.)\s')
TABLE_RE = re.compile(r'^\s*\|')

def _block_type(line: str) -> str:
    if line.startswith('>'):           return 'quote'     # 访谈/引文
    if TABLE_RE.match(line):           return 'table'
    if LIST_RE.match(line):            return 'list'
    return 'text'

class MarkdownParser:
    def parse(self, file_path: str) -> list[dict]:
        with open(file_path, 'rb') as f:
            text = f.read().decode(find_codec(f.read(64) or b''), errors='ignore')
        # ↑ 实际取编码用 find_codec(blob)，这里简化

        blocks, heading_stack, buf, buf_type = [], [], [], None

        def flush():
            nonlocal buf, buf_type
            if buf:
                content = '\n'.join(buf).strip()
                if content:
                    blocks.append({
                        "text": content,
                        "page": 0,
                        "type": buf_type,
                        "heading_path": [t for _, t in heading_stack],  # 章节面包屑
                    })
            buf, buf_type = [], None

        for line in text.split('\n'):
            m = HEADING_RE.match(line)
            if m:                                   # 命中标题
                flush()
                level, title = len(m.group(1)), m.group(2).strip()
                while heading_stack and heading_stack[-1][0] >= level:
                    heading_stack.pop()             # 维护标题栈
                heading_stack.append((level, title))
                continue
            bt = _block_type(line)
            if buf_type and bt != buf_type:
                flush()                             # 类型变了就切块
            buf_type = bt
            buf.append(line)
        flush()
        return blocks
```

**接进 pipeline**（[document_service.py](ruoyi-fastapi-backend/module_rag/service/document_service.py) 的 `process_document`）：
解析 → 每个 block 已带 `heading_path/type` → chunker 把 `heading_path` 前缀到 chunk 内容（`"第一章 > 1.2 定义\n" + 原文`）→ metadata 存 `heading_path/block_type`。
