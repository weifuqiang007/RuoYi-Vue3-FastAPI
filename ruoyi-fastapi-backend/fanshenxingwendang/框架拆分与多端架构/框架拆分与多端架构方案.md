# Part A｜架构方案汇总

## A1. 现状：框架层 vs 业务层边界

当前项目是 **RuoYi-Vue3-FastAPI（insistence 版）**，天生模块化：[common/router.py:384](../../common/router.py) 的 `auto_register_routers` 自动扫描所有 `module_*/controller/` 目录挂载路由。**业务模块即插即用，加一个 `module_xxx` 文件夹就挂一个业务。** 这是拆分能成立的基础。

| 分类 | 后端 | 前端 |
|---|---|---|
| 🟦 **框架层（冻结复用）** | `module_admin`（RBAC/用户/角色/菜单/部门/字典/配置/日志/岗位/在线用户/服务器）、`module_generator`、`module_task`、`common`/`config`/`middlewares`/`exceptions`/`utils`/`server.py`/`sub_applications`/`cli` | `src/views/system`、`src/api/system`、`src/layout`、`src/router`、`src/store`、`src/utils`、`src/directive`、`src/components`（通用） |
| 🟩 **半框架层（AI 基建，可复用）** | `module_ai`、`module_rag` 底层（litellm 多模型 + MinIO + pgvector + 流式） | `src/api/ai`、`src/api/rag` |
| 🟨 **业务层（反身性专属）** | `module_learning`（四区学习/任务/批阅/反思） | `src/views/learning`、`src/views/edu`、`src/api/learning`、`src/api/edu` |

**四个"耦合污染点"**（详见 Part B 的前 3 条 + 散落的 role_key）——框架拆不干净的根源。

## A2. 已确认的三项关键决策

| # | 决策项 | 结论 | 影响 |
|---|---|---|---|
| 1 | **两个产品的部署关系** | ✅ **共享框架代码 + 各自独立部署** | 框架作为共享资产（git submodule / 模板仓库）分发；每个产品 = 框架 + 自己的业务模块 + 自己的库。**不做跨行业多租户共库** |
| 2 | **多端形态与优先级** | ✅ **统一代码、一次打包多端** | 终端 App 需覆盖：iOS App + 安卓 App + Mac 桌面 + Windows 桌面 + 网页；小程序非优先（但保留能力）。选定 **uni-app(Vue3) + Tauri** 路线 |
| 3 | **付费 / 二级分销** | ✅ **暂缓**，未来做成共享模块 | 当前阶段不建 `module_billing` / `module_distribution`；架构上预留位置，不阻塞 |

## A3. 整体架构：一个框架，N 个产品

```
┌─────────────────────────────────────────────────────────────┐
│   框架核心 Core（冻结、版本化、所有产品共享，永不为业务改动）    │
│  RBAC体系 · 配置/字典/日志 · 定时任务 · AI多模型抽象(litellm)    │
│  RAG基建 · 文件存储 · 流式输出 · 传输加密 · 代码生成 · CLI       │
├─────────────────────────────────────────────────────────────┤
│  可复用业务积木（多个产品都能用的通用模块）                      │
│  module_calendar(日历提醒) · module_push(消息推送)             │
│  〔未来〕module_billing(订单/计费/Token) · module_distribution  │
├──────────────────────┬──────────────────────────────────────┤
│  产品A：反身性研修系统  │  产品B：律师代理助理                    │
│  module_learning      │  module_lawyer_case(诉状提炼/流程标准化) │
│  module_rag(专业库)    │  + 复用 calendar / push                 │
└──────────────────────┴──────────────────────────────────────┘
```

- 每个产品**独立部署、独立数据库**，通过框架核心共享代码。
- 框架升级 → 两个产品各自在合适时机同步 submodule 版本即可，互不影响。

## A4. 多端技术方案：uni-app + Tauri

**核心认知：后台管理 ≠ 终端 App，是两个产品。**

| 端 | 服务对象 | 形态 | 技术方案 | 复用度 |
|---|---|---|---|---|
| **后台管理（PC 网页）** | 平台运营/管理员 | 管理控制台 | **直接复用现有 Vue3 + ElementPlus 后台**，按需加日历/推送管理页 | ★★★★★ |
| **终端 App（手机）** | 律师 / 客户 | 消费级 App | **uni-app(Vue3)** → iOS App + 安卓 App + H5 + 小程序 | 全新写 |
| **网页端** | 同终端 App 用户 | 浏览器访问 | = uni-app 编译的 **H5** | 与手机端同一套代码 |
| **电脑端** | 律师桌面 | 可下载应用 | **Tauri** 打包同一套 H5 → Mac + Windows | 与网页端同一套代码 |

**端矩阵覆盖（满足"统一代码、一次打包"）**：

```
               ┌─ iOS App      ┐
uni-app(Vue3) ─┤─ 安卓 App      ├─  ← 一套 Vue3 代码
（业务+API层）  ├─ H5（网页端）  │
               └─ 微信小程序    ┘
                        │
                        │ 同一份 H5 / 共享业务组件
                        ▼
                  Tauri 壳层
                   ├─ Mac 应用
                   └─ Windows 应用
```

**"数据多端一致"天然满足**：手机/网页/电脑本质是同一套前端 + 同一账号 + 同一后端 API，数据在服务端。离线编辑可后期加本地缓存。

**选型理由**：
- 团队已有 Vue3 经验（现有后台即 Vue3），学习成本最低；
- uni-app 一套代码覆盖 iOS/安卓/H5/小程序，律师业务的"端全覆盖"一次解决；
- Tauri 比 Electron 体积小一个数量级（~10MB vs ~150MB），适合给律师装机，且官方支持 Mac + Windows 双端构建。

## 耦合点 2｜server.py 硬依赖 module_rag（改钩子机制）

- [x] **状态：已完成（2026-06-30）** —— 新建 `common/lifecycle.py`（钩子注册表，发现机制照搬 `common/router.py` 的 glob+importlib）；`server.py` 去掉 `from module_rag...` 与 `_init_minio()`，改为 `discover_and_load()`（create_app 里）+ `run_startup(app)`（lifespan 里）。验证：server.py 零业务依赖、钩子 discover/注册/run/fail-soft 机制全过。
  - **后续重构（2026-06-30，见下方"后续重构"小节）**：MinIO 是**通用对象存储基础设施**，不独属 RAG。已把 `MinioClient` 从 `module_rag/utils/` 提升为 `config/get_minio.py` 的 `MinioUtil`（与 `RedisUtil`/`SchedulerUtil` 同列），删除 `module_rag/hooks.py`，预热改回 `server.py` lifespan 直接调用（fail-soft）。`LifecycleHooks` 机制保留给**真正业务专属**的启动逻辑。

### 现状
框架入口 `server.py` 直接 import 并调用业务模块 RAG 的初始化：

- `server.py:18` —— `from module_rag.utils.minio_client import MinioClient`
- `server.py:36-47` —— `_init_minio()` 写在框架生命周期里
- `server.py:111` —— `lifespan` 中调用 `_init_minio()`

**问题**：框架启动逻辑"知道" RAG/MinIO 的存在。换个没有 RAG 的产品（如未来精简版律师后端），框架就得改。

### 目标
框架只提供一个**启动钩子注册表**；业务模块**自己**注册初始化回调；`server.py` 只负责"调用所有已注册的钩子"，不再 import 任何 `module_*`。

### 改动步骤
1. **框架侧新建** `common/lifecycle.py`（钩子注册表）：

   ```python
   # common/lifecycle.py
   from utils.log_util import logger

   class LifecycleHooks:
       _startup = []  # [(name, async_fn), ...]

       @classmethod
       def register_startup(cls, name: str):
           def deco(fn):
               cls._startup.append((name, fn))
               return fn
           return deco

       @classmethod
       async def run_startup(cls, app):
           for name, fn in cls._startup:
               try:
                   await fn(app)
                   logger.info(f'启动钩子[{name}]完成')
               except Exception as e:
                   logger.warning(f'启动钩子[{name}]失败（不阻断启动）：{e}')
   ```

2. **业务侧** `module_rag/hooks.py`（自注册，MinIO 失败不阻断）：

   ```python
   # module_rag/hooks.py
   from common.lifecycle import LifecycleHooks

   @LifecycleHooks.register_startup('rag_minio_init')
   async def _init_minio(app):
       from module_rag.utils.minio_client import MinioClient
       MinioClient.get_instance()
   ```

3. **框架侧新增"钩子发现"**：在 `common/router.py`（或新建 `common/hooks.py`）仿照 `auto_register_routers` 的 glob 方式，扫描并 import 所有 `module_*/hooks.py`，触发装饰器注册：

   ```python
   # 伪代码：discover all module_*/hooks.py and import them
   for path in glob('module_*/hooks.py'):
       importlib.import_module(f'{pkg}.hooks')
   ```

   在 `server.py` 的 `create_app()` 里、`auto_register_routers` 之前调用一次发现函数。

4. **改 `server.py`**：
   - 删除 `from module_rag.utils.minio_client import MinioClient`
   - 删除 `_init_minio()` 整个函数
   - `lifespan` 里把 `_init_minio()` 这行换成 `await LifecycleHooks.run_startup(app)`

### 验证
- `grep -n "module_rag\|module_learning\|module_ai" server.py` 应为**空**（框架入口零业务依赖）。
- 启动后 MinIO 仍正常初始化（日志有 `启动钩子[rag_minio_init]完成`）。
- 故意把 MinIO 配置改错 → 应用仍能启动，仅 warning（不阻断）。

### 风险
- ⚠️ 钩子发现必须保证 `module_*/hooks.py` 被 import 到，装饰器才生效。发现函数的调用时机要在 `run_startup` 之前。建议加一个自检：若某 module 存在 `hooks.py` 但没被注册，启动时 warn。

### 后续重构：MinIO 从业务钩子提升为框架基础设施（2026-06-30）
**起因**：初版把 MinIO 预热放进 `module_rag/hooks.py`，虽达成了"server.py 不依赖业务模块"的目标，却把一个**通用对象存储能力**归类到了**业务模块**下——律师产品同样要用 MinIO，不该向 `module_rag` 取。属归类错误。

**判据**：`MinioClient` 本体是纯通用客户端（put/get/presigned_url/remove/list），零 RAG 逻辑，只读 `config.env.MinioConfig`；配置型、有状态、单例——与 `RedisUtil`/`SchedulerUtil`/`get_db` 完全同列。仓库既有惯例：这类基础设施放 `config/get_*.py`，在 `server.py` lifespan 初始化。

**改动**：
1. `git mv module_rag/utils/minio_client.py → config/get_minio.py`，类名 `MinioClient → MinioUtil`（与 `RedisUtil`/`SchedulerUtil` 命名一致）。
2. `module_rag/service/document_service.py`：import 与 5 处调用改 `from config.get_minio import MinioUtil`。
3. **删除** `module_rag/hooks.py`（MinIO 预热不再走业务钩子）。
4. `server.py` lifespan：在 `init_create_table()` 之后、`LifecycleHooks.run_startup(app)` 之前，加 fail-soft 预热：
   ```python
   try:
       MinioUtil.get_instance()
   except Exception as e:
       logger.warning(f'MinIO 预热失败（对象存储功能将不可用）: {e}')
   ```

## 耦合点 4｜login_service.py 反向依赖业务模块（登录策略钩子化）

- [x] **状态：已完成（2026-06-30）** —— 新建 `common/login_policy.py`（登录校验扩展点注册表，机制照搬 `common/lifecycle.py`）+ `module_learning/hooks.py`（注册审核校验自注册）；`login_service.py` 删掉 `from module_learning.dao.edu_dao import EduDao` 与内联审核块，改为 `await LoginPolicyHooks.run_login_validators(...)`。验证：`module_admin` 对 `module_learning`/`EduDao` **零反向依赖**，机制端到端全过（discover→注册→4 个审核分支行为与原实现逐字一致）。

### 现状（根治前）
耦合点 1 把 `edu_*` 迁出 `module_admin` 后，留下一处**框架→业务反向耦合**：

- `module_admin/service/login_service.py:20` —— `from module_learning.dao.edu_dao import EduDao`
- `module_admin/service/login_service.py:140-148` —— 登录认证通过后，框架登录流程**直接调用** `EduDao.get_audit_by_user_id(...)` 查注册审核状态（待审核/已拒绝则拦截）。

**问题**：框架登录流程"知道"学习业务的注册审核存在。换个没有这套审核的产品（如未来律师后端），框架 `login_service` 就得改——而且方向是反的（框架依赖业务）。

### 目标
框架只提供一个**登录校验扩展点**（默认空，登录正常放行）；业务模块**自己**注册"登录前校验"回调；`login_service.py` 只负责"调用所有已注册的校验器"，不再 import 任何 `module_*`。机制与耦合点 2 的启动钩子一脉相承，但语义不同（见下）。

### 关键设计：fail-fast，不是 fail-soft
| | 启动钩子（耦合点 2，`LifecycleHooks`） | 登录校验器（耦合点 4，`LoginPolicyHooks`） |
|---|---|---|
| 触发时机 | 应用启动（lifespan） | 每次登录认证通过后 |
| 失败语义 | **fail-soft**：单个失败不阻断整体启动 | **fail-fast**：校验器抛 `LoginException` 直接向上抛，产生登录失败响应 |
| 框架是否吞异常 | 是（只记 warning） | **否**（吞了会把"待审核/审核未通过"变成静默放行） |

### 改动步骤
1. **框架侧新建** `common/login_policy.py`（与 `common/lifecycle.py` 同目录、同风格）：

   ```python
   _login_validators: list[tuple[str, Callable[[AsyncSession, int], Awaitable[None]]]] = []

   class LoginPolicyHooks:
       @classmethod
       def register_login_validator(cls, name): ...      # 装饰器，原函数原样返回
       @classmethod
       async def run_login_validators(cls, query_db, user_id):
           if not _login_validators: return              # 空：全新框架/未接业务，直接放行
           for name, fn in _login_validators:
               await fn(query_db, user_id)               # 不兜底，异常原样抛
   ```

2. **业务侧新建** `module_learning/hooks.py`（被 `LifecycleHooks.discover_and_load` 在启动时自动导入，导入即注册）：

   ```python
   @LoginPolicyHooks.register_login_validator('edu_registration_audit')
   async def check_registration_audit(query_db, user_id):
       from module_learning.dao.edu_dao import EduDao    # 惰性 import
       audit = await EduDao.get_audit_by_user_id(query_db, user_id)
       if audit and audit.audit_status == '0': raise LoginException(..., message='账号待审核，请等待管理员审批')
       if audit and audit.audit_status == '2': raise LoginException(..., message=f'账号审核未通过：{audit.audit_remark or "请联系管理员"}')
   ```

3. **改** `module_admin/service/login_service.py`：
   - 删 `from module_learning.dao.edu_dao import EduDao`，加 `from common.login_policy import LoginPolicyHooks`。
   - 把原 139–148 行审核块替换为单行：`await LoginPolicyHooks.run_login_validators(query_db, user[0].user_id)`。

### 验证（已通过）
- `py_compile` 3 文件通过。
- `grep -rn "module_learning\|EduDao\|edu_dao" module_admin/ --include="*.py"` → **零结果**（反向依赖彻底消除）。
- 机制用例：空注册表放行 / fail-fast 传播 / 注册顺序即执行顺序 / 装饰器原样返回原函数。
- **业务钩子端到端**（桩依赖实跑）：discover 导入 `hooks.py` → 注册 `edu_registration_audit`；4 个分支（无记录放行 / status=0 待审核拦截 / status=2 已拒绝拦截带备注 / status=1 已通过放行）行为与原内联代码**逐字一致**。

### 风险
- ⚠️ **注册时机依赖 discover**：登录校验器靠 `LifecycleHooks.discover_and_load()`（在 `create_app` 里、服务接客前）导入 `module_*/hooks.py` 完成注册。若未来有人改了 discover 的调用位置/时机，需确保它仍在服务开始处理请求**之前**执行，否则首次登录可能在校验器注册前放行。`module_rag/hooks.py` 与本钩子共用同一 discover，风险一致。
- ⚠️ 律师产品复用框架时，**不要**让框架 import 任何 `module_lawyer`；律师产品的登录准入（如会员到期、token 额度）应同样经 `LoginPolicyHooks` 自注册到各自的 `module_lawyer/hooks.py`。
