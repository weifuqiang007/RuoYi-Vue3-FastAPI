# 角色权限体系说明（RBAC 三层模型 + 组织架构 + 角色扩展指南）

> **版本**：V1.0
> **日期**：2026-06-26
> **编写人**：后端
> **用途**：梳理本项目（RuoYi-Vue3-FastAPI 二次开发）的权限体系全貌，供后续新增角色时回看。本文为**说明性文档**，不含代码改动。

---

## 0. 一句话总览

本项目的「谁能做什么」由四套机制叠加决定：

| 层 | 机制 | 决定的问题 | 关键表 / 代码 |
|---|---|---|---|
| 层1 | **功能权限**（菜单/按钮） | 能看到哪些页面、能调哪些接口 | `sys_role_menu` + `sys_menu.perms` |
| 层2 | **角色权限**（role_key） | 是什么身份，走哪条业务分支 | `sys_role.role_key` |
| 层3 | **数据权限**（data_scope） | 通用查询里能看到哪些数据行 | `sys_role.data_scope` + `sys_role_dept` |
| 层4 | **教师-班级绑定**（学习模块自定义） | 教师能管哪些班、哪些学生 | `edu_teacher_class` |

> ⚠️ 学习模块的「教师能看到哪些学生」**没有走层3**，而是走层4（显式班级绑定）。新增角色时这是最容易踩坑的点，见第五节。

## 一、组织架构：`sys_dept` 树与「学校 / 班级」的区分

### 1.1 为什么学校名和班级名在同一张表

`sys_dept` 是一张**自引用树形表**，靠 `parent_id`（父节点）和 `ancestors`（祖级链，逗号分隔）表达层级，**没有 `dept_type` 字段**。学校、班级、顶层机构都是这张表里的节点，仅靠**在树中的深度**区分。

字段定义见 `module_admin/entity/do/dept_do.py`：
- `parent_id`：父部门 id（根节点为 0）
- `ancestors`：祖级列表，如 `'0,100,101'`

### 1.2 当前数据的树结构

以生产数据为例（`dept_id` 由序列自动生成，按 `parent_id` / `ancestors` 还原）：

```
社会工作AI研究   (dept_id=100, parent=0,   ancestors='0')          ← 顶层机构/平台  深度0
├── 树人大学      (dept_id=101, parent=100, ancestors='0,100')     ← 学校          深度1
│   ├── 2026级社会工作一班   (parent=101, ancestors='0,100,101')   ← 班级（叶子）  深度2
│   ├── 2026级社会工作二班
│   ├── 2025级社会工作一班 / 二班
│   └── 2024级社会工作一班
└── 长春理工大学  (dept_id=102, parent=100, ancestors='0,100')     ← 学校          深度1
    ├── 2024级社会工作二班   (parent=102, ancestors='0,100,102')
    └── 2023级社会工作一班
```

| 层级 | `ancestors` 令牌数 | 含义 | 示例 |
|---|---|---|---|
| `'0'` | 1 | 顶层机构 | 社会工作AI研究 |
| `'0,100'` | 2 | **学校** | 树人大学 / 长春理工大学 |
| `'0,100,101'` | 3 | **班级**（叶子） | 2026级社会工作一班 |

**核心规律：学校 = 班级的父节点。** 班级的 `ancestors='0,100,101'`，其最后一个令牌 `101` 就是 `parent_id`，也就是学校。两种等价说法：
- `school_id = class.parent_id`
- `school_id = ancestors 字符串里倒数第一个令牌`

### 1.3 为什么现有查询不会把学校名误当班级名

学生档案表 `edu_student_profile.class_id` 注释明确写着「所属班级（复用部门体系）」（`module_admin/entity/do/edu_do.py:15`），即 `class_id` **永远指向班级（叶子）节点**，不会指向学校。

所以 `review_dao.py` 里这段 join 拿到的 `SysDept.dept_name` **一定是班级名**，不存在歧义：

```python
.outerjoin(EduStudentProfile, EduLearningRecord.user_id == EduStudentProfile.user_id)
.outerjoin(SysDept, EduStudentProfile.class_id == SysDept.dept_id)   # 只拿班级
```

**真正缺的是「学校名」**——当前只 join 了一次 `SysDept`，没有往上跳一层。

### 1.4 同时拿到「学校 + 班级」的思路（未实现，仅备选）

再 alias 一次 `SysDept` 当学校表，按 `SchoolDept.dept_id = ClassDept.parent_id` 连上去：

```python
ClassDept = aliased(SysDept)    # 班级
SchoolDept = aliased(SysDept)   # 学校 = 班级的 parent
select(...,
       ClassDept.dept_name.label('class_name'),
       SchoolDept.dept_name.label('school_name')) \
    .outerjoin(ClassDept,  EduStudentProfile.class_id == ClassDept.dept_id) \
    .outerjoin(SchoolDept, ClassDept.parent_id == SchoolDept.dept_id)   # 关键：往上跳一层
```

同样思路也适用于 `review_service.py` 的 `_get_student_info`（当前只取了班级）。

> **若层级可能更深**（学校 → 院系 → 班级），`parent_id` 只能拿到上一级，不一定还是学校。此时应按 `ancestors` 深度取（学校 = 令牌数为 2 的节点），或给 `sys_dept` 加 `dept_type`（'org'/'school'/'class'）字段一劳永逸。当前三层数据用 `parent_id` 足够。

## 二、RBAC 三层模型详解

### 2.1 层1：功能权限（菜单 / 按钮 / 接口入口）

**链路**：用户 → `sys_user_role` → 角色 → `sys_role_menu` → 菜单 → `sys_menu.perms`（形如 `monitor:task:list`）

- 登录时聚合当前用户的 perms 成 `current_user.permissions`，`admin` 拥有通配符 `*:*:*`。
- 接口级强制：`common/aspect/interface_auth.py` 的 `CheckUserInterfaceAuth(perm)`，封装为依赖项 `UserInterfaceAuthDependency('monitor:task:list')`。
- **作用**：控制能看到哪些页面 / 能点哪些按钮 / 能调哪些接口。

### 2.2 层2：角色权限（role_key）

**链路**：`sys_role.role_key`（角色标识串）

- 当前 SQL 内置 `admin`、`common`（`sql/ruoyi-fastapi-pg.sql:188-189`）；业务层又使用了 `teacher`、`student`（注册审核通过后写入 `sys_user_role`）。
- 接口级强制：`common/aspect/interface_auth.py` 的 `CheckRoleInterfaceAuth(role_key)` / `RoleInterfaceAuthDependency('teacher')`。
- 业务代码里**直接读 role_key 做分支**——这是新增角色时要扩展的重点。典型写法：

  ```python
  # module_learning/service/task_service.py:24 / review_service.py:332
  roles = current_user.roles or []        # role_key 字符串列表
  if 'admin' in roles: ...                # 管理员看全部
  if 'teacher' in roles and 'admin' not in roles: ...   # 教师按所管班级过滤
  ```

### 2.3 层3：数据权限（data_scope，通用机制）

**5 档**（`module_admin/entity/do/role_do.py:23-28`）：

| 值 | 含义 | 生成的 WHERE 片段 |
|---|---|---|
| `1` | 全部数据权限 | 无限制 |
| `2` | 自定义数据权限 | `dept_id IN (sys_role_dept 选中的部门)` |
| `3` | 本部门 | `dept_id = 当前用户.dept_id` |
| `4` | 本部门及以下 | `dept_id IN (本部门 + find_in_set(dept_id, ancestors) 命中的子孙)` |
| `5` | 仅本人 | `user_id = 当前用户.user_id` |

- 由 `common/aspect/data_scope.py` 的 `GetDataScope` 依赖项，根据当前用户的 `data_scope` **自动注入一段 WHERE 子句**。
- **作用**：控制同一接口里能查到哪些数据行。前提是目标表有 `dept_id` 或 `user_id` 字段、且业务确实按部门/本人划分。

## 三、本项目的「层4」：教师-班级显式绑定（学习模块自定义）

学习模块的「教师能看到哪些学生」**没有走层3的 data_scope**，而是走显式关联表 `edu_teacher_class`（`module_admin/entity/do/edu_do.py:58`）。

**链路**：教师 user_id → `edu_teacher_class.class_id`（一个教师可绑多个班）→ `edu_student_profile.class_id` → 学生 user_id。

核心实现：`module_learning/service/review_service.py:330` 的 `_managed_student_ids`

```
1. admin → 返回 None（不过滤，看全部）
2. teacher → 取其 edu_teacher_class 绑定的所有 class_id
          → 取这些班级的学生 user_id 列表
          → 用 IN 过滤学习记录
3. 未绑定任何班级 → 返回空列表（查不到任何学生）
```

> **结论**：在这个模块里，决定数据可见性的是「你在 `edu_teacher_class` 里绑了哪些班级」，**不是 `data_scope`**。新增角色时若权限粒度也是「能管哪些班」，应复用/扩展这套机制，而不是配 `data_scope`。

## 四、当前角色清单

| role_key | 角色名 | 来源 | 数据范围机制 |
|---|---|---|---|
| `admin` | 超级管理员 | SQL 内置（role_id=1） | 全部（代码里 `admin in roles` 直接放行） |
| `common` | 普通角色 | SQL 内置（role_id=2） | 由 data_scope 决定 |
| `teacher` | 教师 | 注册审核写入 | `edu_teacher_class` 班级绑定 |
| `student` | 学生 | 注册审核写入 | 仅本人（`user_id`） |

> 注意：业务代码里 `admin` / `teacher` / `student` 是**硬编码字符串**，散落在 `task_service.py`、`review_service.py` 等多处。新增角色需逐处确认。

## 五、新增角色落地步骤（通用清单）

假设要加「教研组长 / 校管理员 / 教学秘书」等新角色：

1. **建角色**：往 `sys_role` 插一行（`role_name`、`role_key`、`data_scope`、`status='0'`）。`role_key` 是代码分支判断的依据，命名要稳定。
2. **配菜单**：往 `sys_role_menu` 插该角色能看到的菜单/按钮 → 控制层1（页面/接口入口）。
3. **发角色**：往 `sys_user_role` 把角色绑给用户（注册审核流程 `apply_role` → 通过后落库；参考 `edu_dao.py:285-299` 的 role_keys 聚合逻辑）。
4. **定数据范围**（二选一或组合）：
   - **走通用 `data_scope`**：适合按部门/本人天然划分、且目标表有 `dept_id`/`user_id` 字段的查询，直接挂 `DataScopeDependency`。
   - **走班级绑定**：权限粒度是「能管哪些班」时，复用/扩展 `edu_teacher_class`（或新建关联表），在 service 里仿照 `_managed_student_ids` 收敛 student_ids。
5. **改业务分支**：在 service 里把新 `role_key` 加进 `if ... in roles` 判断。⚠️ 硬编码判断散落多处，需逐个确认；建议后续抽统一的角色判断工具。

## 六、待决策事项（后续再定）

写本文档时尚未确定，回头需要拍板：

1. **新角色的数据范围走 `data_scope` 还是班级绑定表？**
   - 决定了要不要改 `_managed_student_ids` 这类方法。
   - 典型场景：「校管理员（看本校所有班）」需要先按第一节把学校解析出来，再扩到该校下所有班级——此时会把「学校解析」和「角色权限」两个问题串起来。

2. **要不要给 `sys_dept` 加 `dept_type` 字段？**
   - 现在学校/班级/机构靠树深度**隐式区分**，一旦出现「学校级」权限角色，靠 `parent_id`/`ancestors` 解析学校会变脆弱。
   - 加一个显式类型字段（'org'/'school'/'class'）能让后续所有「学校维度」的权限和数据查询都更稳。
