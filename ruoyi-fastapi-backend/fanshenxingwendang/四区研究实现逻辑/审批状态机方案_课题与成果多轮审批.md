## 一、背景与目标

### 1.1 背景

当前「教师批阅反思研究」模块只支持**一次性点评**，无法支撑真实教学中的**多轮审批循环**：

```
学生提交 → 老师审批 → 需修改则学生重提（状态回到"已提交/待批"）→ 老师再批 → …… → 通过
```

典型场景：学生提交反身性研究成果，老师批阅后认为需要修改，学生根据反馈修改后**重新提交**，老师**再次批阅**，如此循环直到最终通过。课题（学生自研）的**开题审批**也是同样的循环模式。

### 1.2 直接触发问题

教师点评完成后，学生 / 老师 / admin 在 `GET /learning/record/my`（我的研究记录列表）看到的「当前阶段」没有变成「已点评」——点评数据写了，但列表看不到。

### 1.3 目标

1. 让「审批/批阅状态」在记录列表、课题列表可见；
2. 支持 `approved / changes_requested / rejected` 三种决定 + `pending` 待审；
3. 支持**多轮循环**（学生修改后重新提交，回到待审）；
4. **可扩展**：状态机集中、便于未来增加状态/流转/历史留痕；
5. 覆盖两个对象：**学生自研课题的开题审批（edu_task）** + **反思研究成果的批阅（edu_learning_record）**。

## 二、现状与问题分析（已读码 + 连库确认）

### 2.1 点评不写学习记录

[review_service.py:249-285](../../module_learning/service/review_service.py) `submit_comment`（老师提交点评）只做了两件事：

- 写 `edu_review` 表（teacher_comment / review_status='1' / reflection_score）；
- `_sync_to_evaluation` 同步反思维度到终结性评价表 `edu_evaluation`（[review_service.py:489-505](../../module_learning/service/review_service.py)）。

代码注释明说：`# 联动终结性评价表（仅回写反思维度，不计算总分、不改 record 状态）`。
→ **`edu_learning_record` 表在点评前后纹丝不动**。

**连库实锤**（record_id=2）：

| 表 | 字段 | 值 |
|---|---|---|
| edu_review | review_status | `'1'`（已点评）、review_time 有值、有 teacher_comment |
| edu_learning_record | current_stage | `'submitted'`（点评前后没变） |
| edu_learning_record | status | `'submitted'`（没变） |

### 2.2 学生侧 my 接口拿不到点评状态

- 教师批阅列表 [review_dao.py:55-66](../../module_learning/dao/review_dao.py) **已经 JOIN 了 edu_review**，并支持 review_status 筛选；
- 学生侧 [record_dao.py:78-86](../../module_learning/dao/record_dao.py) `get_my_records` **没有 JOIN edu_review**；
- [record_service.py:146-171](../../module_learning/service/record_service.py) `_record_to_dict` 返回字段里也没有任何点评/审批状态。

→ 学生侧列表看不到点评状态。

### 2.3 没有"决定"概念

- [review_vo.py:20-26](../../module_learning/entity/vo/review_vo.py) `TeacherCommentModel` 只有评分 + 评语 + `submit(bool)`，**没有"通过/需修改/驳回"**；
- `current_stage` 的注释（[record_do.py:17-18](../../module_learning/entity/do/record_do.py)）里**设计了 `completed`**（`scenario→...→submitted→completed`），`complete_time` 注释是"教师评分完成、记录关闭的时间"——**但没有任何代码把 record 推进到 completed**，这一步是空的。

### 2.4 课题审批（task 级）整体缺失

- 学生自建课题 `create_task_by_user` / `create_student_task`（[task_service.py:16-48](../../module_learning/service/task_service.py)、[task_service.py:75-93](../../module_learning/service/task_service.py)）创建时直接 `status='1'`（已发布、立即可用），**无审批环节**；
- `edu_task` 表无审批相关字段；
- `task_controller` 无审批接口。

→ "学生提课题、老师审批"这个流程在后端根本不存在。

### 2.5 结论

| 环节 | 现状 |
|---|---|
| 老师点评 → 写 record | ❌ 缺失 |
| my 接口返回点评状态 | ❌ 缺失（没 JOIN） |
| 点评"通过/需修改/驳回"决定 | ❌ 没有 |
| record → completed 流转 | ❌ 设计有、代码无 |
| 课题开题审批 | ❌ 整体缺失 |
| 多轮（学生重提）| ❌ 无机制 |

## 三、总体设计：通用审批状态机

抽出**一个通用的审批状态机**作为核心资产，`edu_task` 与 `edu_learning_record` 两套对象各自挂载、复用同一套状态语义与流转规则。新增文件 `module_learning/service/approval.py`。

### 3.1 状态集合

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `pending` | 待审批/待批阅 | 否 |
| `approved` | 已通过 | 是 |
| `changes_requested` | 需修改（学生可重提） | 否 |
| `rejected` | 已驳回 | 是 |

### 3.2 状态流转图

```
                  学生提交 / 重新提交
                 ──────────────────────►
            ┌──────────────────────────┐
            │                          │
            ▼     老师审批决定          │
        [ pending ] ──── approved ────► [ approved ]  终态·通过
            │   │
            │   └──── rejected ──────► [ rejected ]   终态·驳回
            │
            └──── changes_requested ─► [ changes_requested ]
                                        │  学生修改后重新提交
                                        │  （approval_round + 1）
            └───────────────────────────┘
```

**合法流转**：

- 初始 / 重提 → `pending`
- `pending` → `approved` | `changes_requested` | `rejected`（老师审批）
- `changes_requested` → `pending`（学生重新提交）
- `approved` / `rejected` = 终态

### 3.3 状态机接口（approval.py）

```python
class ApprovalStatus:
    PENDING = 'pending'
    APPROVED = 'approved'
    CHANGES_REQUESTED = 'changes_requested'
    REJECTED = 'rejected'

class ApprovalTarget:
    TASK = 'task'
    RECORD = 'record'

class ApprovalMachine:
    @staticmethod
    def transition(current, decision) -> str   # 老师审批：校验 pending→决定，返回新状态
    @staticmethod
    def resubmit(current) -> str               # 学生重提：changes_requested→pending
    @staticmethod
    def is_terminal(status) -> bool
    @staticmethod
    def can_resubmit(status) -> bool
    @staticmethod
    def label(status) -> str                   # 中文名（待批阅/已通过/需修改/已驳回）
    @staticmethod
    def tag_type(status) -> str                # 前端 el-tag 类型
```

### 3.4 可扩展性落点

- 新增状态（如 `reviewing` / `withdrawn`）或流转，**只改 approval.py 的流转表**一处；
- `approval_round` 字段天然支持多轮统计；
- 预留通用历史表 `edu_approval_log(target_type, target_id, round, decision, comment, operator_id, operate_time)`，未来需要**跨轮完整留痕**时启用，不影响现有逻辑；
- `ApprovalMachine` 可复用于未来其他审批场景。

| 新增字段 | 类型 | 默认 | 说明 |

## 五、后端设计

### 5.1 接口清单（阶段 1：成果批阅）

| 方法 | 路径 | 说明 | 角色 |
|---|---|---|---|
| PUT | `/learning/record/resubmit/{record_id}` | 学生修改后重新提交（changes_requested → pending，round+1） | 学生 |
| PUT | `/learning/record/advance/{record_id}` | （已有）推进阶段；到 submitted 时同步 approval_status='pending' | 学生 |
| PUT | `/learning/review/comment/{record_id}` | （已有）老师点评；**入参新增 decision**，按决定设 record 审批状态 | 教师/admin |
| GET | `/learning/record/my` | （已有）**响应新增 approval_status / approval_round / review_status** | 所有 |

`TeacherCommentModel` 入参新增：
```python
decision: Literal['approved','changes_requested','rejected'] | None
# submit=true 时必填
```

`submit_comment` 按 decision 经 `ApprovalMachine.transition` 设 record：

- `approved` → `record.status='completed'`、`current_stage='completed'`、`complete_time=now`（落实一直没实现的 completed 流转）；
- `changes_requested` / `rejected` → 对应 approval_status；同步写 `edu_review.decision`；
- `submit=false`（草稿）→ 不改 `record.approval_status`。

### 5.2 接口清单（阶段 2：课题审批）

| 方法 | 路径 | 说明 | 角色 |
|---|---|---|---|
| PUT | `/learning/task/submit-approval/{task_id}` | 学生提交/重提课题待审（→ pending，round+1） | 学生 |
| POST | `/learning/task/approve/{task_id}` | 老师审批课题（decision + comment） | 教师/admin |

逻辑要点：

- `create_task_by_user`（学生自研）建时 `approval_status='pending'`（不再立即可用）；
- `approve_task`：`approved` → `status='1'`（学生方可开始）；其余 → 对应状态；
- `RecordService.start_task` **加校验**：学生自研课题（creator_type='1'）必须 `approval_status=='approved'` 才能开始，否则提示「课题待审批」；教师任务（creator_type='0'）不受影响。

## 八、验证方案（端到端）

### 阶段 1

1. 学生走完四区 → advance 到 submitted：`approval_status='pending'`；
2. 老师批阅选「需修改」+ 评语：record `approval_status='changes_requested'`，`edu_review.decision` 落值；
3. `/learning/record/my` 列表显示「需修改」；
4. 学生「重新提交」：record 回 `pending`、`approval_round=2`，老师侧重新出现待批；
5. 老师选「通过」：`status='completed'`、`current_stage='completed'`、`complete_time` 落值；列表显示「已通过」；
6. 老师选「驳回」：`approval_status='rejected'`，学生不可重提。

### 阶段 2

1. 学生创建自研课题：`approval_status='pending'`，列表显示「待审批」、不可进入；
2. 老师「需修改」→ 学生改后「重新提交」(round+1) → 老师「通过」→ `status='1'`，学生方可 start_task；
3. 老师「驳回」→ 学生不可开始。

### 回归

- 教师任务（creator_type='0'）全流程不受影响；
- 旧已点评记录回填为 approved 后，my 列表正确显示。

## 九、风险与注意事项

1. **`start_task` 权限校验变更**（阶段 2）会影响学生开始课题的既有行为，需确保教师任务（creator_type='0'）不受影响、旧自研课题回填为 approved。
2. **草稿与决定解耦**：`submit=false`（保存草稿）不应改 `record.approval_status`，避免老师暂存评语时误触发状态流转。
3. **completed 流转**首次落地，需确认前端「已完成」阶段的展示与跳转（MyRecordList 已支持 completed 文案，但进入入口需评估）。
4. **多轮留痕**：当前方案以 `approval_round` 记轮次、`edu_review.decision` 记本轮决定；若评审要求每轮意见都保留，再启用 `edu_approval_log` 历史表（不破坏现有设计）。
5. **数据库变更**需在 dev/test/prod 库分别执行，`edu_approval.sql` 保持幂等。
