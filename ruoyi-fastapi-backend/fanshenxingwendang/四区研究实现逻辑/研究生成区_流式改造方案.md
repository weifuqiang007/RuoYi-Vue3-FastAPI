## 一、改造背景

研究生成区的四个 AI 功能（生成候选问题、生成论文框架、AI 辅助撰写章节、推荐参考文献）原均使用**非流式调用**：

```python
result = await AiCall.call_llm_json(db, model_id, prompt)      # 非流式 JSON
result = await AiCall.call_llm_non_stream(db, model_id, prompt) # 非流式文本
```

LLM 推理耗时通常 10-30 秒，前端 axios 全局超时 10 秒，导致用户点击按钮后接口超时，白屏等待体验差。

**改造目标**：全部改为 SSE 流式输出，用户点击后能看到 AI 逐字生成过程，不再超时。

## 二、流式架构设计

### 2.1 后端：AsyncGenerator + StreamingResponse

```
Controller 层:
  @research_controller.post('/xxx/stream')
  async def xxx_stream(...) -> StreamingResponse:
      stream = ResearchService.xxx_stream(query_db, ...)
      return StreamingResponse(content=stream, media_type='text/event-stream')

Service 层:
  @classmethod
  async def xxx_stream(cls, db, ..., model_id=1) -> AsyncGenerator[str, None]:
      # 1. 校验数据
      # 2. yield {"type": "status", "message": "AI 正在生成..."}
      # 3. 流式调用 AiCall.call_llm_stream(), 逐 chunk 转发
      # 4. 流结束后 parse_llm_json() 解析 → 保存到 DB
      # 5. yield {"type": "result", "data": {...}} 发送最终结构化结果
```

**SSE 消息类型**：

| type | 说明 |
|------|------|
| `status` | 状态提示（"正在生成..."） |
| `content` | 逐字内容（每条一个字符，逐字打字效果） |
| `result` | 最终结构化结果（JSON 对象） |
| `error` | 错误信息 |

### 2.2 前端：fetch + ReadableStream

```javascript
// 通用流式请求封装
function streamFetch(url, data, callbacks, signal) {
  const { onStatus, onContent, onResult, onError } = callbacks
  return fetch(url, { method: 'POST', body: JSON.stringify(data), signal })
    .then(response => {
      const reader = response.body.getReader()
      // 逐行解析 JSON，按 type 分发回调
    })
}
```

**使用原生 `fetch` 绕过 axios 10 秒全局超时**。

### 2.3 向后兼容

- 所有非流式接口保持不变
- 每个功能同时存在 `/xxx`（非流式）和 `/xxx/stream`（流式）两个端点
- 前端流式失败时自动 fallback 到非流式

## 四、数据流

```
用户点击按钮
  → fetch POST /learning/research/xxx/stream
    → Controller: StreamingResponse
      → Service.xxx_stream (AsyncGenerator)
        → yield {"type":"status","message":"正在生成..."}
        → AiCall.call_llm_stream 逐 chunk
          → 每个 content chunk 拆为单字符 yield
        → parse_llm_json → 保存到 DB
        → yield {"type":"result","data":{...}}
  ← onContent 逐字更新 streamText（用户实时看到）
  ← onResult 更新最终数据，清空 streamText
```

## 五、后端 Prompt 设计

流式场景下 LLM 直接输出可读文本（非 JSON），便于逐字展示：

| 功能 | Prompt | 输出格式 |
|------|--------|----------|
| 生成候选问题 | `RESEARCH_QUESTION_STREAM_PROMPT` | 编号列表：1. 研究问题：... 选择理由：... 研究路径：... |
| 生成论文框架 | `RESEARCH_FRAMEWORK_STREAM_PROMPT` | 编号列表：1. 绪论 章节说明：... |
| AI 辅助撰写 | `CHAPTER_DRAFT_PROMPT`（原有） | 纯文本写作建议（约500字） |
| 推荐参考文献 | `REFERENCES_STREAM_PROMPT` | 编号列表：1. 作者. 标题... 关联说明：... |

流结束后后端用正则解析文本为结构化数据（先尝试 JSON 解析，失败则正则匹配），保存到数据库。

## 九、V1.2 保存完整性与刷新回显

> **变更日期**：2026-06-12
> **变更原因**：用户反馈点击"保存"后刷新页面，之前保存的内容全部丢失

### 9.1 问题分析

原始设计存在两个缺陷：

1. **后端 `init_research`**：当 research 已存在时，每次都重新聚合前三区材料并**覆盖** `material_summary`，且只返回 `research_id` + `material_summary` 两个字段。前端拿不到 `candidate_questions`、`selected_question`、`framework`、`chapters`、`ref_literature`，刷新后全部重置为空。
2. **前端 `saveAll()`**：V1.1 版本只保存当前激活的章节，其他章节内容丢失。

### 9.2 后端改造：`init_research` 已存在时返回完整数据

**改动文件**：`research_service.py` — `init_research()` 方法

**改动内容**：

```
首次进入（research 不存在）：
  → 聚合前三区材料 → 创建 research → 返回基础数据 {research_id, material_summary}

刷新/再次进入（research 已存在）：
  → 不覆盖任何字段 → 直接返回 get_detail() 完整数据
  → 包含：research_id, material_summary, candidate_questions, selected_question,
          framework, ref_literature, chapters[{chapter_id, chapter_index, chapter_title,
          content, ai_suggestion, status}], status, create_time
```

**关键**：不再执行 `research.material_summary = material_summary` 覆盖操作，保留用户保存的内容。

### 9.3 后端改造：`save()` 方法保存所有章节

**改动文件**：`research_service.py` — `save()` 方法，`research_vo.py` — `ResearchSaveModel`

**改动内容**：

- `ResearchSaveModel` 新增 `chapters` 字段（`Optional[list]`，每项含 `chapter_index` + `content`）
- `save()` 方法接收 `chapters` 列表后，遍历调用 `ResearchDao.get_chapter_by_index()` + `update_chapter()` 逐个更新
- 返回 `saved_chapters` 列表记录已保存的章节序号

### 9.4 前端改造：`saveAll()` 一次保存全部

**改动文件**：`index.vue` — `saveAll()` 方法

**改动内容**：

```javascript
await saveResearch({
  research_id: researchId.value,
  selected_question: selectedQuestion.value || null,
  material_summary: materialSummary.value || null,
  chapters: chapters.value.map(c => ({
    chapter_index: c.chapter_index,
    content: c.content ?? '',
  })),
})
```

一次请求保存所有数据，不再逐个调用 `/chapter/save`。

### 9.5 刷新回显数据流

```
用户刷新页面
  → init() 调用 initResearch(recordId)
    → 后端 init_research: research 已存在
      → 返回 get_detail() 完整数据
  ← 前端解析响应:
    research_id       → researchId
    material_summary  → materialSummary
    candidate_questions → candidateQuestions
    selected_question   → selectedQuestion
    framework           → framework
    ref_literature      → references
    chapters[]          → chapters (normalizeChapter)
  → 页面完整回显上次保存的所有内容
```

## 十、V1.3 修复"重新汇总"功能失效

> **变更日期**：2026-06-17
> **变更原因**：实测点击"重新汇总"后，material_summary 始终返回 `"情境：无\n决策数：0\n反思：无"`，即使前三区已填满数据

### 10.1 问题分析

V1.2 改造时为支持刷新回显，把 `init_research` 改成"research 已存在就跳过聚合、直接返回 DB 旧值"。这引入了回归 bug：

```python
research = await ResearchDao.get_by_record_id(db, record_id)
if research:
    return await cls.get_detail(db, record_id)   # ← 永远走这里，聚合代码被跳过
```

**结果**：首次创建 research 时（当时前三区可能为空）写入了错误的 `"情境：无..."`，之后这个值被"冻结"在 DB 里，"重新汇总"按钮永远读不到前三区的真实数据。

同时发现一个潜伏 bug：聚合代码用了 `ReflectionDao.get_by_record_id()`，但反思区 dao 里**根本没有这个方法**（只有 `get_list_by_record_id`）。只是因为聚合代码被跳过没执行，才没报错。

### 10.2 后端改造：init_research 增加 force 参数

**改动文件**：`research_service.py`

```python
async def init_research(cls, db, record_id, student_id, model_id=1, force=False):
    """force=False（页面加载）：已存在则回显；force=True（重新汇总）：强制重新聚合"""
    research = await ResearchDao.get_by_record_id(db, record_id)
    if research and not force:
        return await cls.get_detail(db, record_id)   # 回显，不覆盖

    material_summary = await cls._aggregate_material(db, record_id)  # 强制重新聚合
    if research:
        research.material_summary = material_summary  # 只更新材料，保留其余字段
        ...
    else:
        # 首次创建
        ...
    return await cls.get_detail(db, record_id)   # 返回完整数据
```

**关键点**：
- 抽出 `_aggregate_material()` 私有方法，集中前三区聚合逻辑
- `force=True` 时只更新 `material_summary`，**不覆盖** candidate_questions / framework / chapters 等已有内容

### 10.3 后端改造：修正 reflection 查询 + 丰富材料内容

**改动文件**：`research_service.py` — `_aggregate_material()`

```python
@classmethod
async def _aggregate_material(cls, db, record_id) -> str:
    scenario = await ScenarioDao.get_by_record_id(db, record_id)
    decisions = await DecisionDao.get_by_record_id(db, record_id)
    reflections = await ReflectionDao.get_list_by_record_id(db, record_id)  # ← 修正方法名

    # 情境：描述前300字
    # 决策：列出每个节点简述（最多5条）
    # 反思：取最新一条前300字
    return f"情境：{...}\n决策数：{...}条\n  · 节点：动作...\n反思：{...}"
```

修复点：
1. `ReflectionDao.get_by_record_id` → `ReflectionDao.get_list_by_record_id`（消除 AttributeError）
2. 反思取 `reflections[0]`（最新一条），因为返回的是 list
3. 决策区不再只显示数量，列出每条节点的简述，材料更丰富
