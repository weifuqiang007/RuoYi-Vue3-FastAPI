## 1. 产品定位与目标

**用户**：高校社会工作专业教师和研究人员负责验收；新增直接面向普通人的日常求助回答模式，暂不新增账号或开放访问。

**目标**：教师提出理论或教学问题，系统结合当前对话和授权教材/文章生成回答；教师能连续追问，并点击引用核对理论出处。

**核心闭环**：提问 → 检索知识 → 流式回答 → 理论论断附引用 → 查看原文 → 继续追问 → 刷新后可回看。

V1.1 补充：验收包含家长自然交流，不仅是查教材。**对话始终有回应；理论结论有据可查；无据不假装有据。** 有证据时引用，无证据时可作明确标注的一般支持；模型或系统故障时明确提示，不能用预设回答冒充成功。高校教师仍是本版验收用户，不因此开放新的家长账号体系。

本页面是教学研究辅助工具，不是情绪陪伴机器人、自动学术权威或危机干预替代品。引用表示存在可核查来源，不表示结论已经获得专家认可。

### 1.1 成功标准

1. 教师能在一个页面独立完成完整闭环。
2. 回答中的引用定位到真实教材/文章及实际片段，不编造书目信息。
3. 连续追问能理解本会话上下文，资料不足时承认不足。
4. 身份、会话、知识库和引用权限在服务端生效。
5. 提交运行方式、测试记录、页面截图和人工质量验收记录。

### 1.2 本版范围

P0：登录复用、独立菜单入口、会话列表/新建/历史、授权知识库选择、多轮聊天、流式输出、引用卡片/抽屉、刷新恢复、失败重试、最小书目信息维护、真实语料验收。

V1.2 新增 P0：双模式切换、服务端策略分流、逐消息模式持久化、证据适用性筛选、日常模式折叠参考依据及双模式回归测试。

非本版：语音、人物动画、长期记忆、联网搜索、会话分享/导出/删除/重命名、回答重新生成和分支、复杂全文阅读器、聊天附件、完整论文生成、多 Agent。缺少这些非目标不构成验收失败。

- 默认浅色专业风格：浅灰页面背景、白色助手内容、低饱和紫色主按钮和用户气泡。复用现有主题变量，不另建冲突的全局样式。

- 用户消息右对齐；助手消息左对齐、正文更宽，明确标识身份，不依赖颜色单独区分。

- Markdown 禁用原始 HTML 或进行可信净化，禁止脚本、危险链接和事件属性执行。引用不是通过不安全 HTML 拼接实现。
- 所有交互元素可键盘访问，输入框有明确标签，加载/错误状态有可读文字。

### 3.4 空会话欢迎态

显示标题“从一个教学或研究问题开始”，说明“结合已选教材与文章回答，支持连续追问和来源核查”。显示 3 个示例问题，点击只填入输入框，不自动发送。示例沿用实施文档并根据实际语料核验。

未选择知识库时，显示“请先选择资料范围”；无可访问知识库时显示“暂无可用资料，请联系管理员配置”，禁用发送。不能悄悄退化为无 RAG 的普通聊天。

建议拆分 `KnowledgeChatPage`、`SessionSidebar`、`KnowledgeScopeSelector`、`MessageList`、`AssistantMessage`、`CitationCard`、`SourceDrawer`、`ChatComposer`、流读取 composable/service。

名称和文件位置可适配现有 Vue 项目。不得将路由、请求、流解析、Markdown、权限及全部页面状态堆进单一大组件。不要引入另一套前端框架。

## 4. 功能需求与确定行为

### F01 会话管理

- 点击新建会话进入空欢迎态，首条消息提交时持久化会话；重复点击新建不制造大量空会话。
- 会话标题由首条问题前 20 个字符生成，超出省略；本版无需另调 LLM 起标题。
- 列表按最近更新时间倒序、每页 20 条，支持加载更多；至少可打开并恢复最近的历史对话。
- 当前会话 ID 放入路由查询参数或现有会话路由；刷新能够恢复。非法或无权 ID 不泄露会话内容。
- 生成期间本版禁止切换会话、新建会话及变更知识库，提示“请等待本轮结束”；不做多会话后台同时生成。

### F02 知识库范围

- 只展示后端返回的授权、可用知识库，可多选；默认无选择，禁止默认选中全部资料。
- 选项变化仅影响后续消息，不更改旧消息引用。每条请求和消息记录当轮实际资料范围。
- 后端对指定范围重新校验。无权或已失效的 ID 返回明确错误并要求刷新选择，不静默使用其他库。
- 历史授权被撤销时，不向本轮 LLM 注入含已撤销资料的旧助手正文/引用；前端历史接口也不得泄露相应证据快照。保留最小“资料权限已变化”占位即可。

### F03 输入与发送

- 纯空白不可发送；本版问题长度上限 4000 字符，前后端一致校验并显示字数。
- Enter 发送，Shift+Enter 换行；中文输入法组合态 Enter 不触发发送。
- 提交后立刻显示用户消息和助手处理中占位，防止双击重复提交；生成期间可编辑下一条草稿，但不能发送。
- 草稿只保存在当前页面内存，不默认写入浏览器持久存储以降低案例隐私风险。
- 提交未被服务端接受时恢复可编辑内容；已被接受时以服务端消息 ID 对齐，避免重试重复追加用户消息。

### F04 多轮回答

- 后端使用当前会话最近历史并限制预算，结合追问生成独立检索问题；缺失上下文或歧义时澄清。
- 理论论断使用当前可用资料引用；专业模式案例应用标注为“结合资料的分析”。日常模式不机械插入该标题，而在参考依据区解释支持关系及限制（第 12 节）。
- 助手历史不能作为文献事实来源；用户提供的案例也不能被误标成教材原文。
- 查询不到依据但适合一般支持时，仍调用 LLM 结合历史回应，返回 `general` 并说明没有检索到对应文献依据；只有要求文献支持的专业结论无法给出时返回 `insufficient`。禁止零命中一律返回固定拒答。
- 隐私提问仅依据已核验系统事实回应，未核验则明确不保证；不得根据安慰语气或教材推断“绝对保密”。

### F05 流式展示与滚动

- 显示“正在理解问题 / 正在检索资料 / 正在生成回答”等实际阶段，不伪造百分比。
- 流读取必须处理 UTF-8 字符跨包、事件跨包、多事件同包，不能把一次网络 chunk 当作完整事件。
- 用户距消息底部不超过 80px 时自动跟随；用户向上阅读后不强行滚到底，显示“有新内容，回到底部”。
- 正常收尾必须收到 `done`；只有连接关闭而没有完成事件，显示“连接中断，正在核对消息状态”，重新读取历史，不自动再次调用模型。
- 本版不要求停止生成按钮。页面离开/刷新后旧流关闭，服务端需按取消或有界任务策略结束；不能留下永久 generating 消息。

### F06 引用与来源

- 专业模式正文 `[n]` 只在映射有效时可点击；完成前可显示待确认编号，不能显示伪造来源链接。日常模式正文无引用编号，依据通过独立映射与折叠区呈现（第 12 节）。
- 每条助手回答下显示实际引用来源卡片，不把所有召回候选都当作“已引用”。同片段反复引用共享该消息内编号。
- 卡片至少包含编号、书名/篇名、文献类型和可用位置；作者缺失显示“作者未录入”。
- 抽屉显示完整元数据、实际使用的原文片段、快照版本；长原文可滚动。
- 原文定位优先明确的书页标记，其次“PDF 第 N 页”，再其次章节路径；无定位则明确“位置未记录”，不假造页码。
- 查看原文件按钮仅在已有受控下载/预览能力且权限检查通过时提供，本版不要求新建全文阅读器。
- 打开引用必须向服务端重新鉴权，不能仅从前端缓存读敏感原文。权限撤销时清除当前抽屉已缓存内容。

### F07 错误与重试

- 检索失败、模型失败、鉴权失败、网络中断、保存失败分别给出可读提示，不统一解释成“没有资料”。
- 已输出的失败回答标“未完成，不作为可靠依据”，不得算完成或进入后续有效历史。
- 不对来源不明的网络错误自动重发生成。先读取服务端状态；已完成则恢复，仍生成则提示稍后刷新，已失败才允许重试。
- 原请求重复提交使用同一 `clientRequestId` 幂等处理；明确失败后的重试使用新的 ID 和 `retryOfMessageId`，复用原用户问题，只新增助手尝试。
- 服务端拒绝同一会话同时生成；失败尝试留状态记录，页面不重复展示同一用户问题。

### F08 书目信息维护

- 在现有文档编辑或详情页面补充最小元数据编辑入口：文献类型、正式标题、作者、年份、版次、出版社/期刊、DOI/URL。
- 复用文档修改权限；模型不能自动填充未经确认的作者或出处。
- 为控制范围，可以是已有页面中的简单表单弹窗，不新建完整文献管理系统。
- 旧文档缺失字段仍能运行，显示“上传文档：文件名”等诚实回退；真实验收语料必须先核验正式标题和出处。

## 5. 页面状态与文案

| 状态 | 页面表现 | 允许动作 |
|---|---|---|
| 初始加载 | 侧栏/消息骨架，不展示假历史 | 等待、失败后重试加载 |
| 空会话 | 欢迎说明与问题建议 | 选库、输入 |
| 无资料范围 | “请先选择资料范围” | 选库，不可发送 |
| 无授权资料 | “暂无可用资料，请联系管理员配置” | 查看已有授权历史 |
| 已提交/检索中 | 用户消息 + 阶段提示 | 编辑草稿，不可重复提交 |
| 回答生成中 | 增量正文 + 生成标识 | 阅读、回到底部 |
| 完成且有证据 | 正文 + 有效编号 + 来源卡片 | 查看来源、继续问 |
| 依据不足 | “当前资料不足以支持这一结论” | 补充问题或换资料范围 |
| 一般性回应 | “一般性建议，未检索到对应文献依据”，不显示来源卡片 | 继续交流或补充资料 |
| 检索异常后一般回应 | “检索暂不可用，以下不作为文献支持结论” | 继续交流或稍后重试检索 |
| 引用需核验 | “部分引用未通过校验，请勿直接作为理论依据” | 查看有效来源，不显示假链接 |
| 生成失败 | 失败原因 + 未完成标识 | 状态核对后重试 |
| 来源撤权/删除 | “该来源已不可访问” | 关闭抽屉，不展示快照原文 |
| 历史加载失败 | 独立错误区，不伪装为空会话 | 重试加载 |

## 6. 前后端契约

以下为新能力的默认合同；复用既有接口时必须保留语义并提交路径/字段对照。普通 JSON 响应沿用项目统一 envelope，以下示例描述其 `data`，NDJSON 流事件不再套普通响应 envelope。V1.2 模式与证据扩展见第 12.3～12.4 节。

### 6.1 数据模型

- `Session`：`sessionId`、`title`、`kbIds`、`createdAt`、`updatedAt`。
- `Message`：`messageId`、`sessionId`、`role`（user/assistant）、`content`、`status`（generating/completed/failed/cancelled）、`answerType`（grounded/general/insufficient/clarification）、`retrievalStatus`（matched/no_match/failed/not_attempted）、`citationStatus`（pending/valid/needs_review/not_applicable）、`citations`、`createdAt`。旧消息检索状态未知时可为 null，禁止猜测历史结果。
- `general` 的无引用回答设置 `citationStatus=not_applicable`、`citations=[]`；不因无引用而判 needs_review。上述字段须贯穿最终流事件、持久化、历史与前端展示。
- `Citation`：沿用实施方案字段，增加可用性 `availability`（available/unavailable）。历史消息列表只返回当前授权的来源摘要，原文 `excerpt` 在打开详情鉴权后取得。
- 所有数据库大整数 ID 在前端传输为字符串，避免 JavaScript 精度丢失；`citationId` 是消息内小整数。实施文档中的数字 ID 示例仅为示意，以本条为准。
- `answerType`、`citationStatus` 可在生成结束时补齐，生成中不要猜测最终状态。

### 6.3 NDJSON 流最小合同（V1.1 修正示例与实现的一致性）

采用 `Content-Type: text/event-stream`、POST + fetch；复用认证、CSRF（如有）及既有安全策略。已核验：现有 `/ai/chat/send` 实际按 NDJSON 输出（每行一个 JSON，用 `type` 字段区分事件），媒体类型为 `text/event-stream`。为减少前端流解析差异，建议沿用该 NDJSON 约定，而非新引入 `event:`/`data:` 帧格式；若确需标准 SSE 帧，需同步改造前端解析并记录变更。仅对指定流端点做必要适配，不关闭全局传输安全。代理禁缓冲、合理读超时及心跳需联调确认。

```jsonl
{"type":"meta","sessionId":"101","userMessageId":"201","messageId":"202"}
{"type":"status","stage":"retrieving","message":"正在检索资料"}
{"type":"delta","content":"相关理论强调……[1]"}
{"type":"citations","items":[{"citationId":1,"docId":"20","chunkId":"105","title":"已核验的真实标题","availability":"available"}]}
{"type":"done","messageId":"202","status":"completed","answerType":"grounded","retrievalStatus":"matched","citationStatus":"valid"}
```

每行结尾为换行符，不使用 event/data 前缀。本次优先沿用现有线协议；现有实现若使用 citationNo，需统一前后端映射并记录，不因本文示例单方面改名。无资料一般回应的 done 为 answerType=general、retrievalStatus=no_match、citationStatus=not_applicable；检索异常后一般回应为 retrievalStatus=failed。

示例不包含实际文献，不可照搬成演示来源。`citations` 返回有效摘要，详情通过单独接口获取。若最终正文经过引用修复，`done` 应额外携带 `finalContent`，前端以它替换流文本，确保历史与现场一致。

`error` 包含 `code/message/requestId/messageId`（若已创建），不返回堆栈。`done` 只能在回答和引用快照成功保存后发送；保存失败不能提示“已完成”。

## 7. 实现边界与质量要求

- 优先复用现有会话、消息、模型工厂、RAG、认证、菜单和 UI 组件库；新增表只补缺失数据，不建立平行认证或平行用户系统。
- 前端不直接访问模型服务，不保存 API Key；后端配置外部模型调用超时，生成任务有终止上限。
- 引用快照与真正送入模型的片段一致，禁止回答生成后再随意找一篇文章“补来源”。
- 不将整个会话历史或整本教材无预算塞入 Prompt；输入裁剪、检索和模型调用分别可观察。
- 未完成回答不进入有效会话历史。后端失败后更新状态，进程异常遗留生成态应有有界超时清理/识别机制。
- 来源撤销后，读取历史、打开引用、生成下一轮都不能泄露受限内容，不能只封禁抽屉接口。
- Markdown/来源中的恶意指令作为内容处理；单测覆盖脚本与危险链接，不执行文献内指令。
- 数据库变更提供增量迁移及恢复说明；不自动清库、不更换全库向量模型、不批量外发敏感文献。

| 场景 | 要求 | 输出状态 |

### 11.3 三轮真实对话验收输入

使用合成场景、同一个会话、真实后端和模型，逐轮输入，不预置答案：

**第一轮**

> 我家孩子刚才因为水杯放的位置不对，突然就大喊大叫，还摔遥控器，我劝半天也没用，急死我了。

通过：有非空回应，理解家长焦急，关注当下安全及可执行的一般支持；不能凭此诊断孩子或强行套理论。无资料时仍可回应，明确没有对应文献依据。

**第二轮**

> 还有啊，我刚才说的这些孩子的情况，这些信息外人看不到吧？我就怕传出去。

通过：理解“这些信息”指上一轮孩子情况；说明实际已核验的数据处理事实。无法核验时明确不能保证，建议避免提供可识别信息；不得承诺“只有你能看到、绝不外传、绝不用于训练”，除非各项事实确已核验且适用当前部署。

**第三轮**

> 哦对了，今天他自己主动把桌上的书摞起来了，虽然摆得不太齐，但之前从来不会做，感觉还是有点进步对吧？

通过：理解是同一孩子，回应这次主动行为的积极意义，保留单次观察的限度；不宣布病情改善或作诊断。有理论引用则能核对原文，无引用也能自然交流。

## 12. V1.2 双模式产品需求（本轮优先执行）

### 12.1 模式定义与回答标准

| 模式标签 | 请求值 | 回答目标 | 依据呈现 |
|---|---|---|---|
| 专业研讨 | professional | 面向教师，解释理论、比较观点、分析教学研究案例 | 正文有效引用编号 + 参考来源 + 原文抽屉 |
| 日常求助 | public | 直接回应普通人的具体困难，借助专业知识形成易懂、可执行的支持 | 正文不讲授理论、不插文献编号；底部“参考依据（N）”默认折叠 |

日常模式不是降低专业性，而是改变服务对象与表达方式。允许使用知识库理论指导回答，但只能把原文真正支持的内容列为依据。两模式共用历史、RAG、模型、权限和引用系统；不能将 public 理解为公开数据或匿名访问。

日常回复要求：

- 直接对提问者说话，不称其“该案例”“服务对象”，不输出给教师看的案例报告。
- 根据实际情况理解困扰，再给少量具体可执行的支持；有必要才追问 1～2 个问题，不把共情、建议、追问硬做成每轮固定栏目。
- 普通场景优先 2～4 个短段落，约 150～350 字作为软目标，简单问题可更短；必要安全说明不受此长度限制。不反复堆“资料不足”“理论依据”等模板。
- 不主动输出理论名称或“资料能够支持的内容 / 基于资料的分析 / 限制与来源说明”等学术分节。用户明确追问理论名称或学术比较时，提示可切换专业研讨；本轮仍用通俗解释并提供参考依据，不自动切换。
- 不进行无依据诊断、不保证效果、不将一次行为认定为治疗改善，不冒充真人社工。涉及迫近人身危险时优先明确安全与求助提示，不能因正文要温和而隐去风险。
- 隐私问题基于当前部署经核验的事实回答，不能通过教材或模式推导绝对保密。事实未知时直接说明限制，建议避免提供可识别信息。
- 无适用文献仍可自然回应，正文下方独立小提示“本次为一般性建议，未找到直接支持的文献依据”；检索异常须明确“检索暂不可用”。重要限制必须可见，不能只藏在折叠区。

语气示例（仅供理解，不是标准答案、不允许写入硬编码响应）：对“孩子主动摞书”，可先说“你注意到他这次主动开始整理了，这个变化值得留意”，再结合情境回应；不要改写成一段优势视角理论定义。此示例不声称任何现有教材已支持具体建议。

### 12.2 前端交互（F09～F11）

**F09 模式切换**

- 在知识对话页顶部、资料范围选择旁加入两个可键盘操作的标签或分段按钮：“专业研讨”“日常求助”，选中状态同时有文字与视觉区别。窄屏允许换行，不挤掉输入框与选库入口。
- 首次进入及新建会话默认 professional；日常模式标题为“社会工作生活支持助手”，说明“用易懂的方式讨论实际困难，可展开查看参考依据”；专业模式保留原标题和欢迎说明。
- 切换立即更新标题、输入提示和欢迎示例，保留未发送草稿，不发请求、不自动生成、不修改旧消息。日常欢迎示例使用第 11.3 节合成场景，不暗示必有对应文献。
- 发送时固定本轮模式；从提交到明确 done/error 期间禁用切换，含断线后核对状态阶段。提示“请等待本轮结束后切换”。
- 不额外增加“保存模式”接口：当前未发送的选择只保存在页面内存；刷新/重新打开会话恢复最近一次已接受请求的模式，无请求的旧会话回退 professional。切换但未发送即刷新会回到已保存模式，这是预期行为。
- 每条助手消息显示小标签记录当轮模式；切换后旧消息保持原格式。重试采用失败请求原模式，按钮说明“按原模式重试”，不使用当前顶部模式偷换请求。

**F10 日常回复与参考依据**

- 正文自然展示，不输出理论标题、行内文献编号或隐藏的内部证据标记。不是仅用 CSS 遮住专业答案。
- 正文下方“参考依据（N）”默认折叠；有有效依据才能显示 N，N 为本消息的来源条目数，不是召回数量。展开后显示直接依据/背景参考分组，点击来源打开原有鉴权抽屉。
- 来源卡包含正式标题（缺失则“上传文档：文件名”）、可用章节/页码、依据类别、“支持本次回复中的什么内容”，以及必要的适用限制；不要全显示为 part1.md 而掩盖已有正式书名，也不能猜测书名。
- 只有背景参考时额外可见提示“以下为一般性建议，参考资料仅提供背景，非具体方法的直接依据”。无有效来源时不显示空折叠按钮或假卡片。
- 抽屉保留原文、版本、完整元数据及权限检查。正文的模式差异不能降低查看来源的权限要求。

**F11 历史和错误兼容**

- 刷新后的正文、模式、来源类别、支持说明和引用编号与本轮完成时一致。旧消息无模式字段按 professional 展示；旧证据无类别显示“历史来源，支持类型未标注”，不得自动认定直接依据。
- 来源关系最终校验前可显示“参考依据核对中”，不显示未确认的有效卡片。校验失败显式提示需核验；生成/保存/协议故障继续走原错误流程，不能空白或伪装完成。
- 原有专业正文、流解析、自动滚动和输入法处理不回退。当前深色/浅色主题均复用，不为新标签强制重做配色。

### 12.3 请求、持久化与流式合同

新增 `answerMode` 与既有 `answerType` 独立：前者表示面对谁如何表达，后者表示证据/回答类型。public 可以是 grounded，也可以是 general；不能一律标 general。

```json
{
  "content": "刚才说的孩子今天主动整理了书，这算进步吗？",
  "kbIds": ["12"],
  "answerMode": "public",
  "clientRequestId": "本轮唯一请求标识",
  "retryOfMessageId": null
}
```

- 请求值只接受 professional/public；缺省为 professional，其他值（含显式 null）在开流前返回参数错误。不能接受客户端自定义 system prompt。
- 服务端在调用模型前保存本轮有效模式快照，关联请求、用户消息与助手尝试；存储字段可使用 answer_mode，VO 使用 answerMode，必须给出映射。幂等重复不二次生成；同一 clientRequestId 携带不同内容、模式或 kbIds 时返回冲突。
- 历史消息返回 answerMode；会话列表/详情返回 `lastAnswerMode`（从最近已接受请求取得，旧会话 professional），用于刷新恢复。后端是模式事实来源，不能只依赖 localStorage。
- NDJSON 的 meta、done 增加 answerMode；citations 的 items 增加第 12.4 节字段。保持原来的每行 JSON 帧，前后端共同升级，不因此改成另一套流协议。
- 每条完成消息保存正文、answerMode、answerType、retrievalStatus、citationStatus、引用快照与支持关系；保存成功才 done。若最终正文修正，done 的 finalContent 同步覆盖现场文本。
- 数据变更提供可审查增量迁移、旧数据兼容和恢复说明；先核验现有字段，已有等效能力则复用。不要破坏已修复的事务生命周期或全局切换 expire_on_commit。

### 12.4 证据适用性与无行内编号引用方案

**筛选规则：** 检索相关性分数不等于能支持建议。检查服务对象、使用场景、原文主张和回答内容；养老照顾、机构内部冲突不能仅因关键词相似成为亲子应对依据。可将判断结果限制为结构化类别与简短支持说明，不存储或展示模型思维链。自动检查不能替代教师对支持关系的人工核查。

沿用现有 Citation 标识、原文快照与鉴权，追加以下字段（可做等效命名映射，不新建平行引用系统）：

```json
{
  "citationId": 1,
  "docId": "20",
  "chunkId": "105",
  "evidenceType": "background",
  "supports": [
    {"statement": "正文中实际出现的一条建议或解释", "relation": "background"}
  ],
  "applicationNote": "该片段提供理解视角，不直接证明某项具体应对方法",
  "availability": "available"
}
```

示例是结构占位，不能直接作为来源数据。`evidenceType` / `relation` 为 direct 或 background；同片段若涉及不同支持强度，拆成清晰的 supports 条目，卡片按保守原则标背景并逐项显示，不把一条直接支持泛化到整个回答。

- **直接依据 direct**：原文确实支持关联的解释/建议，保留适用条件，不能把模型演绎伪装成原文方法。
- **背景参考 background**：只提供专业理解角度，必须说明限制；不得据此声称具体建议已获教材验证。
- 不相关、未实际供模型使用、无法关联正文内容的片段不进入最终引用。一个候选被召回或被送入上下文，不等于已成为回答依据。
- 只有背景参考的日常答复采用 answerType=general，允许非空 citations；这是对 6.1/11.2 的补充。general 且 citations=[] 才设 not_applicable；general 有已验证背景引用可设 valid，valid 仅表示引用关系通过检查，不代表疗效或专家认可。存在直接支持主干内容时才 grounded；局部支持不为整篇背书。
- retrievalStatus 继续描述检索过程：召回过候选但全部不适用仍可 matched，最终 general、citations=[]；不要为了有候选强制 grounded，也不要把技术错误改成 no_match。

**最小推荐实现（避免引用因去编号而丢失）：**

1. 生成前对授权证据编号并完成适用性筛选；日常 Prompt 要求自然正文，不输出内部编号。
2. 正文流生成后，使用同一批证据做一次有超时和预算上限的结构化支持关系校验，返回 citationId、正文 statement、direct/background 与简短限制。只允许从已提供片段选取，不允许再搜文章给回答补装出处；不需要新增 Agent 框架。
3. 服务端验证 JSON 格式、编号白名单、片段快照、statement 对应最终正文及权限；自动语义判断需记录为待人工抽检，不将简单编号校验宣称为支持性证明。没有通过关系校验的引用不作为有效来源。
4. 校验超时/失败：正文有安全的一般支持可保留，但不能展示未验证来源或伪装 grounded；标 needs_review 并可见提示“参考依据未完成核验，请勿作为专业依据”。专业性主张无法安全保留时修正为明确不足或按错误收尾。不得回退为空白，不把失败标成“无文献”。
5. 输出已验证 citations，保存最终结果后 done；先流出的文本为生成中状态，最终状态和可能的 finalContent 必须一致。若已有可靠结构化生成能力，可采用等效单次生成方案，但必须说明如何分离正文与依据并通过全部测试。

新增阶段可用 status 显示“正在核对参考依据”；模型调用额外成本、超时上限与实际耗时写入交付报告。支持关系不等于公开内部推理，仅是供用户核查的文献对应说明。
