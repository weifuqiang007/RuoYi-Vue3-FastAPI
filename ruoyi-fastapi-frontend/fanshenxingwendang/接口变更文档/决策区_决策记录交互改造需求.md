# 接口/交互变更文档：决策区决策记录交互改造

> **版本**：V1.0  
> **日期**：2026-06-11  
> **提出人**：前端联调需求整理  
> **用途**：提交给架构师、后端工程师评估可行性与接口改造方案  

---

## 一、背景

当前“决策区”页面已经支持：

- 保存决策记录
- 查询某条学习记录下的决策记录列表
- 点击“编辑”将某条决策记录回填到表单

但当前交互存在以下问题：

1. 页面首次进入时，表单默认是“新建空白决策”，不会自动回填已有决策内容。
2. 同一个关键事件下允许存在多条决策记录，但界面没有“当前选中决策”的明确表达。
3. 决策记录列表显示 `ID` 的意义不强，用户更关心“当前选中了哪一条决策”。
4. 列表仅支持“编辑”，不支持删除无效/废弃的决策记录。

因此需要对“决策区”进行一次交互与接口联合改造。

---

## 二、当前页面现状

当前前端页面位置：

- `src/views/learning/decision/index.vue`
- `src/views/learning/decision/components/DecisionForm.vue`
- `src/api/learning/decision.js`

当前已有接口：

| 接口 | 说明 |
|---|---|
| `GET /learning/decision/list/{record_id}` | 获取当前学习记录下的决策记录列表 |
| `POST /learning/decision/save` | 新增决策记录 |
| `PUT /learning/decision/save` | 更新决策记录 |
| `PUT /learning/decision/confirm/{record_id}` | 确认决策区完成 |

当前列表展示字段：

- ID
- 事件
- 行动
- 操作（仅“编辑”）

当前表单行为：

- 页面初始化后调用 `newDecision()`，生成空白表单
- 只有点击“编辑”后，才会把某条记录回填到表单

## 三、目标改造效果

### 3.1 页面首次进入时自动回填最近更新的一条决策记录

#### 目标行为

当某个学习记录下已经存在决策记录时：

- 前端进入决策区后，自动从决策记录列表中找出**更新时间最近**的一条记录
- 将该记录内容自动回填到顶部 `DecisionForm` 表单中
- 同时将这条记录视为“当前选中的决策”

当不存在任何决策记录时：

- 仍维持当前行为，展示空白表单

#### 需要后端确认

为了准确判断“更新时间最近”，列表接口需要满足以下其中一种方式：

1. **推荐方案**：`GET /learning/decision/list/{record_id}` 返回 `create_time`
2. 或者后端保证列表默认按 `create_time DESC` 排序，前端直接取第一条

#### 建议

还是后端按照create_time 降序排序。前端默认取第一条

---

### 3.2 决策记录列表去掉“ID”列，改为“点选当前决策”

#### 目标行为

列表第一列不再显示数据库 `decision_id` 数字，而改为一个“选择框”或“单选框”。

用户点击某一条记录时，表示：

- 我当前正在查看/编辑/操作的是这条决策记录
- 这条记录应立即回填到上方表单
- 右侧联动区域（如伦理分析面板）也应跟随当前决策切换

#### 交互建议

推荐使用以下任一形式：

1. **单选框列**（推荐）
   - 一次只能选中一条
   - 语义清晰，能明确表达“当前决策”
2. **行点击选中**
   - 点击整行即可选中
   - 需要高亮当前行

#### 设计原因

因为同一个关键事件下可能存在多种不同的决策方案，用户真正需要的是：

- 明确知道“当前使用哪一条决策”
- 明确控制“当前编辑的是哪一条”

而不是关心数据库里的 `decision_id` 数字。

---

### 3.3 在“编辑”后增加“删除”按钮

#### 目标行为

每条决策记录的操作列中，除了“编辑”，还要增加“删除”按钮。

点击删除后：

- 弹出确认提示
- 用户确认后删除该条决策记录
- 刷新列表

删除后的前端行为建议：

- 如果删除的不是当前选中记录：仅刷新列表即可
- 如果删除的是当前选中记录：
  - 若列表还有其他记录，则自动选中“更新时间最近”的一条并回填表单
  - 若列表已空，则恢复为空白新建表单

#### 需要新增后端接口

建议新增：

```http
DELETE /learning/decision/{decision_id}
```

或：

```http
DELETE /learning/decision/delete/{decision_id}
```

具体路径由后端统一风格决定。

#### 删除规则建议

后端需要明确：

- 是否允许删除任意未确认决策
- 是否仅允许删除当前用户自己的决策记录
- 决策区已确认后是否仍允许删除
- 删除是否为逻辑删除（推荐）还是物理删除

## 四、建议的接口改造点

### 4.1 决策记录列表接口出参建议新增字段

接口：

```http
GET /learning/decision/list/{record_id}
```

建议 rows 中至少补充以下字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `decision_id` | int | 记录唯一标识，前端内部仍需要 |
| `key_event_index` | int | 关键事件索引 |
| `action_taken` | string | 列表展示 |
| `reasoning` | string | 表单回填 |
| `psychological_state` | string | 表单回填 |
| `alternatives` | string | 表单回填 |
| `expected_outcome` | string | 表单回填 |
| `actual_outcome` | string | 表单回填 |
| `is_intervened` | bool | 表单回填 |
| `key_event_desc` | string | 表单回填 |
| `ethics_analysis` | object / null | 右侧联动 |
| `update_time` | string | 用于判定最近更新记录 |
| `create_time` | string | 辅助展示/兜底排序 |

> 如果当前接口已经返回其中大部分字段，则只需确认是否补充 `update_time`。

---

### 4.2 建议新增删除接口

建议接口：

```http
DELETE /learning/decision/{decision_id}
```

返回示例：

```json
{
  "code": 200,
  "msg": "删除成功",
  "data": {
    "decision_id": 12
  }
}
```

## 五、前端改造建议

### 5.1 初始化逻辑

当前：

- `loadDecisionList()`
- `newDecision()`

建议改为：

1. 加载列表
2. 判断列表是否为空
3. 若不为空：
   - 按 `update_time` 倒序选中最新记录
   - 回填 `currentDecision`
4. 若为空：
   - 执行 `newDecision()`

---

### 5.2 列表结构建议

当前列：

- ID
- 事件
- 行动
- 操作（编辑）

建议改为：

- 当前决策（单选/点选）
- 事件
- 行动
- 操作（编辑、删除）

其中：

- “当前决策”列用于表达选中状态
- 不再向用户展示 `decision_id`

---

### 5.3 表单回填规则

当发生以下任一操作时，都应将对应记录反向渲染到 `DecisionForm`：

- 页面首次进入且存在历史记录
- 点击列表行/单选框切换当前决策
- 点击“编辑”
- 删除当前选中记录后自动切换到其他记录

## 六、关键业务规则待确认

以下规则建议由架构师/后端统一明确：

1. **“更新时间最近”** 的判断依据是否以 `update_time` 为准？
2. 如果 `update_time` 为空，是否回退到 `create_time`？ 是的，需要回退
3. 删除是否允许发生在“决策区已确认”之后？ 是的，可以的。
4. “当前决策”的概念是否仅是前端交互状态，还是需要后端落库保存？ 也需要后端落库。

### 关于“当前决策”是否需要后端保存

目前你的需求里，“当前决策”更像是一个**前端选择态**，未必需要落库。

两种可能：

- **方案A：仅前端选择态（推荐）**
  - 用户当前选中哪条记录，仅影响表单回填和右侧联动
  - 不新增数据库字段
  - 实现成本低

- **方案B：后端持久化当前决策**
  - 例如给某条决策记录增加 `is_current = 1`
  - 可跨端、跨刷新记住“当前决策”
  - 需要新增表字段、保存逻辑、互斥约束

如果业务只是“同一个事件下可以尝试多个决策版本”，通常 **方案A 足够**。

## 七、验收标准

### 场景1：存在历史决策记录

- 进入决策区后，表单自动显示最近更新的一条决策
- 列表中该条记录处于选中状态

### 场景2：切换当前决策

- 点击另一条记录的选择框/行后
- 表单立即切换为该记录内容
- 右侧联动区域也切换到对应内容

### 场景3：删除非当前决策

- 列表删除成功
- 当前表单内容不变

### 场景4：删除当前决策

- 若仍有其他决策，则自动选中最近更新的一条并回填
- 若无剩余决策，则恢复空白表单

### 场景5：无历史决策

- 页面首次进入显示空白表单
- 列表为空

---

## 八、结论

本次需求本质上不是简单样式调整，而是一次**决策区记录选择机制的改造**，涉及：

- 前端列表展示改造
- 前端初始化与回填逻辑改造
- 后端列表字段补充（建议补 `update_time`）
- 后端新增删除接口
- 删除后的联动规则确认

建议先由架构师明确“当前决策”是否需要后端持久化，再由后端补齐接口能力，最后前端联调落地。
